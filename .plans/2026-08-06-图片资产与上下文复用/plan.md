# 图片资产与上下文复用计划

目标：将进入 Agent 的图片保存为内容寻址资产，只执行一次 OCR/视觉摘要；当前轮首次请求携带压缩图，后续步骤和历史请求默认只携带稳定引用与解析结果，需要重新查看时再按引用一次性加载图片。

范围：仅修改 Rust `vw-agent`。复用 `.plans/2026-08-06-底层图片压缩/` 的进程内压缩结果，新增按项目/会话隔离的图片资产存储、分析缓存、首轮直传策略、只读重看工具和引用清理。补充独立测试并执行仓库要求的 Clippy。

范围外：不使用 Python、ImageMagick、FFmpeg、系统命令或外部压缩服务；不提高 Gateway/HTTP 请求体上限；不依赖供应商文件 ID、对象存储或新增桌面 UI；不把原图、Base64、OCR 文本或视觉摘要写入日志。

前置依赖：必须先完成 `.plans/2026-08-06-底层图片压缩/1-统一压缩图片再编码.md`，本计划不重复实现图片压缩。

## 已确认缺陷

- 本地、远程和 data URI 图片最终都会被转为 Base64 data URI；Base64 约有额外体积开销，多图和长历史会持续放大请求。
- Desktop 每次提交完整聊天历史，`prepare_messages_for_provider` 会重新处理历史中的图片标记，因此旧图片会重复进入模型请求。
- 现有 OCR 只在旧 Agent 循环和 Gateway 简单聊天路径中调用，主 Desktop session processor 没有接线。
- 现有 OCR 结果没有稳定写回图片资产；工具循环可能对同一图片重复提取。
- 当前图片标识是路径或 data URI，不是稳定、可隔离、可去重的图片 ID。
- 现有 `ImageInfoTool`/`FileReadTool` 不能安全表达“按当前会话图片 ID 重新看一次原图”。

## 设计决策

- 图片第一次进入时计算完整 SHA-256，以 `image_id` 作为稳定内容引用；资产按 `app_session_scope` 隔离，无项目范围时退回当前 session 范围，禁止跨范围解析。
- 原始字节与压缩后的模型输入均保存在 `global.paths().data` 下的持久目录，不使用会随版本清理的通用 cache 目录。
- 元数据只保存版本、MIME、尺寸、字节数、创建/访问时间和引用关系；不记录源路径、Base64 或解析正文。
- 写入采用临时文件加原子重命名；同一范围内相同哈希去重，并用进程内按键互斥避免并发重复分析。
- 图片分析为一次专用视觉调用，结构化返回“可见文字”和“视觉摘要”；缓存键包含图片哈希、分析模型和提示词版本，版本变化时允许重新分析。
- 分析模型优先使用已配置且有效的 `multimodal.ocr.model`；否则仅在当前模型明确支持图片时使用当前模型；均不可用时返回明确错误，不伪造分析结果。
- 当前用户请求中新加入的图片只在首次成功的 LLM step 直接携带；该 step 的网络重试可重复携带，成功后本轮工具循环立即改用引用和缓存文本。
- 历史图片、恢复会话中的图片以及后续新请求默认只传 `image_id`、OCR 和摘要，不传路径、data URI 或图片字节。
- 模型通过只读 `image_asset_read` 工具请求重看。工具只登记当前范围内的 `image_id`，下一次 LLM step 一次性注入图片，成功后恢复文本表示；工具结果本身不返回 Base64。
- 删除会话只释放引用；同一范围仍被其他会话引用的资产继续保留，最后一个引用释放后再删除图片和分析缓存。

## 请求状态流

1. 请求入口扫描图片标记，完成资产写入或解析已有 `image_id`。
2. 缺少有效分析缓存时执行一次 OCR/视觉摘要，并保存结构化结果。
3. 当前新图片在首次成功 LLM step 使用压缩图；历史图片使用引用和分析结果。
4. 首次成功后，内存消息视图将当前图片也替换为引用和分析结果。
5. 模型需要复核细节时调用 `image_asset_read`；下一 step 只注入被请求图片一次。
6. 会话删除或引用更新时执行范围内引用回收。

## 安全与体积边界

- 所有压缩、哈希、落盘和读取均由 Rust 进程内代码完成。
- 源图片仍受已有数量、MIME 和源字节上限控制；压缩输出仍受前置计划定义的尺寸和请求总预算控制。
- OCR 与视觉摘要视为不可信图片内容，必须使用已有中和边界并限制长度，不能被当作系统指令。
- `image_asset_read` 不接受任意文件路径，只接受当前请求上下文可见的 `image_id`。
- 不通过提高 HTTP/LLM 请求上限掩盖重复发送；回归证据必须证明历史和首个成功 step 后不再出现 `data:image` 或 `[IMAGE:/...]`。

## 开发策略

- 按五个批次顺序实施：资产存储、分析缓存、上下文策略、按需重看、生命周期回归。
- 行为变更先写测试；仓库禁止未经用户要求运行 `cargo test`，所以不执行测试命令，以 Clippy 编译全部测试目标、聚焦差异和结构化 fixture 审查作为验证证据。
- 每个任务只修改列出的模块，不顺带改 Desktop UI、网关上限或供应商协议。
