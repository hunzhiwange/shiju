## 先写失败测试

1. 在共享 provider 状态测试中覆盖默认限制常量：未知模型得到 `context=32768`、`input=28672`、`output=4096`，显式 `limit` 不被默认值覆盖。
2. 在 resolver 测试中读取内置 `shiju`，断言每个模型都有正数 `limit.context`；对 `api.json` 扫描时排除空 provider，不允许可调用模型缺失 `limit` 或为 0。
3. 在 agent provider 测试中验证同一自定义模型配置经过 agent 解析后与 resolver 得到相同限制和能力默认值。
4. 增加数据审计测试或等价的无写入检查，确保 `limit.context`、`limit.output` 和能力对象的字段类型正确，且没有把图像/音频/视频模型误标成文本输出模型。

建议先运行对应的聚焦测试确认失败，再实现；不要先改 JSON 让测试“自然通过”。

## 实现步骤

1. 在共享 provider 层集中定义默认上下文、默认输入和默认输出常量，并提供统一的“配置值优先、基线值其次、默认值最后”的限制解析路径。正数配置才视为有效，`0` 只表示明确不适用的输出，不得再让 `context=0` 绕过自动压缩。
2. 让 `vw-provider-resolver` 和 `vw-agent` 使用同一套限制兜底；保留已有 `builtin_model_limit` 入口的兼容性，避免桌面端和运行时各自维护不同默认值。
3. 以 `models.dev` 当前目录作为 `api.json` 的大规模基线，逐项查找缺失限制的模型。优先使用模型厂商官方页面；对阿里模型优先参考百炼模型页和 Coding Plan FAQ。每条记录补齐 `limit` 以及已公布的 `reasoning`、`tool_call`、`temperature`、`attachment`、`modalities` 等字段。
4. 补齐 `shiju.json` 的全部 34 个条目，重点核对 Qwen、DeepSeek、GLM、MiniMax、embedding、rerank、图像模型的实际用途与窗口，不能把同名模型在不同 provider 的限制直接复制过去。
5. 对官方资料没有给出精确窗口的条目使用集中默认值，并在任务交付说明中列出这些模型 ID、默认原因和后续可替换的资料来源；不保留“看似完整但来源不明”的精确数字。
6. 保持 JSON 顺序和现有格式风格，避免无关重排；解析失败时返回清晰错误或使用已有内置回退，不静默吞掉坏数据。

## 完成标准

- `shiju.json` 的 34 个模型全部有可解释的限制和能力字段。
- `api.json` 中缺失项全部补齐；不适用字段有明确结构语义，未知上下文使用统一默认值而不是 0。
- resolver 与 agent 的同一输入得到相同限制结果，默认值和显式值都有测试保护。
