## 先写失败测试

1. 为模型草稿新增字段写状态测试：打开现有模型能恢复 `limit`、能力布尔值、输入/输出模态和 `family`；新增模型能使用默认值但不丢失用户输入。
2. 为模型弹窗写视图/消息测试，覆盖上下文、最大输入、最大输出、推理、工具调用、温度、附件、输入/输出模态和编辑回填。
3. 为保存 patch 写测试：只写入已填写的 `limit` 与能力字段，空数字被拒绝或按默认处理；重新保存已有模型时保留未编辑的 `id`、headers、options 等字段。
4. 为解析链路写测试：自定义 JSON 中显式字段覆盖内置基线，未填写字段沿用基线或任务 1 的安全默认值，resolver 与 agent 结果一致。

## 实现步骤

1. 扩展 `CustomProviderModelDraft` 与 `CustomProviderModelModalState`，用字符串承载数字输入以支持编辑态；为限制和能力增加清晰的字段名，不把 UI 文案直接当作配置 key。
2. 扩展 `SettingsMessage` 与 `updates.rs` 的打开、输入、校验、保存、取消分支。编辑已有模型时按索引回填；模型 ID 修改时检查重复项，避免静默覆盖另一个模型。
3. 在 `custom_model_modal.rs` 增加暗色主题兼容的分组表单：限制区、能力区、输入模态区、输出模态区。数字字段显示单位为 token，并明确空值表示“使用默认/基线值”。滚动条继续保持 4px；中文标签不得使用等宽字体。
4. 修改 `custom_provider_patch_from_draft`，按 `shiju.json` 结构写入 `name`、`family`、能力字段、`modalities` 和 `limit`。删除或留空字段时只清理对应覆盖，不影响同模型的其它已有配置。
5. 在 resolver 与 agent provider 解析时读取这些模型级覆盖，而不是只读取模型名称和 headers。对未知模型沿用默认文本能力与任务 1 的默认限制；对已有基线模型只覆盖用户显式设置的字段。
6. 为自动发现模型保留现有合并行为：新发现模型使用默认限制/能力，用户可在保存前逐个编辑；自动发现不得覆盖已有模型的手工限制。

另外手工检查一次暗色主题下的新增/编辑弹窗：输入非法数字、保存、重新打开、取消和删除模型都应有可见且不泄露密钥的反馈。

## 完成标准

- 添加和编辑自定义模型都能设置上下文/输入/输出限制与参考结构中的能力字段。
- 保存后配置文件、resolver、agent、设置页四处字段一致；未填写限制不会产生 `context=0`。
- 非法数字、超出关系约束和重复模型 ID 都有明确错误，不静默保存。
