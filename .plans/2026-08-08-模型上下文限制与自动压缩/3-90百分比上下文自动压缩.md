# 任务 3：90% 上下文自动压缩

- 状态：未开始
- 批次：3
- 依赖：任务 1、任务 2
- 预估工作量：1—1.5 个工作日
- 预计修改文件：`session/processor` 上下文治理/运行器、共享限制读取、压缩和处理器测试
- 目标：在活跃会话下一次模型请求前检测有效输入使用率，达到/超过 90% 时自动释放上下文。

## 先写失败测试

1. 为纯判断函数写边界测试：89% 不触发，正好 90% 和 90% 以上触发；`input` 有值时优先使用 `input`，没有时按 `context - 输出预留` 计算。
2. 覆盖 `context=0`、负数/缺失 usage、默认限制、输出限制大于窗口等异常输入，要求安全回退且不 panic。
3. 为活跃处理器增加下一请求前的测试：首次请求按估算值判断；收到真实 `input_tokens` 后工具结果使上下文越过阈值时，下一次 `llm_runner` 调用前先压缩。
4. 为压缩结果写协议测试：保留系统消息、最近用户/助手消息和工具调用配对，旧工具结果被占位或裁剪，压缩不会重复执行或无限重试。

## 实现步骤

1. 在 `context_governance` 增加单一的阈值/有效窗口计算和压缩入口。统一使用任务 1 的默认限制与任务 2 的模型覆盖；删除或改造 `compaction.rs` 内 70% 的重复判断，避免两个阈值同时存在。
2. 在 `runner.rs` 的每轮 `llm_runner::run_llm_step_with_retry` 之前执行压缩预检。优先使用上一轮响应的真实 `input_tokens`；没有真实 usage 时，按系统提示、工具定义和序列化消息做保守估算，并给新增工具结果留出估算空间。
3. 压缩顺序固定为：清理更早的工具结果内容、裁剪更早的非系统历史、必要时压缩大块工具输出；每一步都保护系统提示、最新对话和工具调用/结果协议配对。不要把原始工具载荷写入日志或新增请求。
4. 压缩后重新估算；若仍达到阈值，继续执行一次有限的更强裁剪；若仍无法满足则发出明确的上下文超限错误并停止本轮，不能在同一轮无界循环。
5. 在日志中记录会话 ID、步骤号、压缩前后估算 token、模型限制和清理项数量，不记录消息正文、API Key 或工具原始输出。保留现有 `StepStart`/`StepFinish` 语义，压缩应发生在下一次 `StepStart` 之前。
6. 为 ACP/非 ACP、usage 为零和多模态消息保留兼容分支；模型限制只负责预算，不能改变图片资产权限和已有请求协议。

## 验证命令

```bash
cargo test -p vw-agent --lib context_governance
cargo test -p vw-agent --lib compaction
cargo test -p vw-agent --lib processor::runner
cargo test -p vw-agent --lib processor::llm_runner
cargo clippy --all-targets --all-features -- -D warnings
```

需要结合测试日志确认：压缩发生在下一次模型请求前，而不是模型已经返回 length limit exceeded 之后；发生错误时不会自动重试同一份超限消息。

## 完成标准

- 90% 阈值在真实和估算 usage 两条路径都生效，默认/自定义/内置模型限制一致。
- 自动压缩可重复运行且有上限，协议配对和关键系统上下文完整。
- 旧 70% 孤立判断不再影响运行时，相关测试与文档阈值统一为 90%。
