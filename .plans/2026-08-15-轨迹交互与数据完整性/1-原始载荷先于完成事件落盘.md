# 任务 1: 原始载荷先于完成事件落盘

批次：【批次 1】 无

状态：未开始

目的：消除 `StepFinish` 已到达但对应 `session_step_llm_raw` 尚未写入或因接收端退出而永不写入的竞态。

来源任务：用户反馈“最后一条好像没有成功写入，有时候历史有原始数据”。

预计会话范围：只调整 processor 的工件写入结果与事件顺序，并补充聚焦测试；不改变网关路由、桌面重试或轨迹 UI。

## 上下文

- `runner.rs` 当前先调用 `on_event(StreamEvent::StepFinish)`，再调用 `persist_llm_raw_step_payload`；接收端返回 false 会直接跳过落盘。
- `ui_store::persist_llm_raw_step` 把 scope、store 和数据库错误压成 `None`。新增可返回错误的窄接口供 processor 使用，保留确有调用价值的兼容包装即可。

## 测试计划

- 行为：观察到 `StepFinish` 时 raw 已可读；即使事件接收端拒绝 `StepFinish`，raw 也已经持久化。
- 失败验证测试：在 `runner_tests.rs` 新增 `raw_payload_is_visible_before_step_finish` 与 `raw_payload_survives_rejected_step_finish`；在 `artifacts_tests.rs` 覆盖失败结果不再被静默吞掉。
- 失败验证命令：`cargo test -p vw-agent raw_payload_is_visible_before_step_finish --lib`
- 预期失败原因：当前回调在 raw 写入之前触发，回调内读取为空；回调返回 false 时后续写入不会执行。
- 通过验证命令：`cargo test -p vw-agent raw_payload_ --lib`
- 模拟策略：使用现有隔离 session store fixture 和真实 SQLite 写读；只模拟 LLM step 输出及事件回调。

## 步骤

1. 先新增证明事件顺序和接收端提前退出问题的失败测试。
2. 运行失败验证并确认 raw 在 `StepFinish` 回调时尚不可见。
3. 为 ui_store 增加保留具体错误的写入路径，让 `persist_llm_raw_step_payload` 返回可判断结果。
4. 在 runner 中把 raw 写入移到 `StepFinish` 发布前；失败时带 session_id、step_index 记录 warning，但继续发布模型完成事件。
5. 运行聚焦测试及全仓 clippy，审查未改变 AI 调用摘要和最终回答路径。

## 完成

完成时应能从 `runner.rs` 的顺序、`artifacts.rs` 的返回结果和聚焦测试证明：完成事件绝不会先于启用状态下的 raw 写入尝试，接收端退出也不会丢失该步骤 raw。
