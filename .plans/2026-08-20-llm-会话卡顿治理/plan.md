# LLM 会话卡顿治理计划

目标：消除 LLM 会话期间的用户操作卡顿，并缩短模型增量从底层产生到桌面可见的应用内延迟。

范围：桌面端活动请求订阅、首轮会话保存、相同历史刷新、流式增量合并与持久化、尾消息渲染、工具结果卡片、网关 LLM 首增量转发，以及 OpenSkills 同步进入会话前的关键路径。

范围外：模型供应商网络耗时、模型推理速度、工具自身执行时间、数据库引擎替换、全仓库 UI 重构和新增可配置性能开关。

假设：当前工作区已有六个相关文件的未提交草案，分别尝试异步保存会话元数据、保留相同历史的 UI 状态和简化工具结果卡片；它们属于用户改动，实施时必须保留、审查并用当前证据验证，不能覆盖或直接视为已完成。

## 底层分析

- `App::subscription` 在每次 UI 更新时克隆每个活动 `AgentRequest`；该类型含完整 `Vec<ChatMessage>` 历史，因此输入、动画和流事件期间都会产生与总历史大小成正比的复制。
- `session::start` 在发送入口构造请求、缓存快照和保存本地会话时多次复制历史；新会话元数据原生路径原先还会同步等待网关请求。现有草案已把该网关请求改成 `Task::perform`，仍需验证。
- 活动会话增量被 `ACTIVE_STREAM_DELTA_FLUSH_INTERVAL = 1s` 固定延后；每次刷新又会全量扫描增长中的尾消息、克隆尾消息做 UI 预热，并构造完整会话快照保存。直接缩短间隔会放大 CPU、分配和 IO。
- LLM 处理器首个模型请求前同步加载配置、扫描工作区/插件技能、解析指令、预取文件；`ensure_open_skills_repo` 还可能在请求线程执行 clone/pull，造成间歇性首包卡顿。
- LLM 侧 33ms/1024 字符合并器不会保证第一个小增量立即发出；桌面侧收到后还会经过上述 1 秒窗口，因此“模型慢”和“模型已返回但 UI 晚显示”目前无法从体验上区分。
- 网关终态消息与轨迹持久化发生在 `Done` 后，会影响完成确认但不是首增量前的直接阻塞点；本计划不改其事务语义。

## 设计决策

- 先把活动请求改为共享不可变载荷，使订阅重建只复制引用；罕见的会话重置使用写时复制。
- 将“界面增量刷新”和“完整会话保存”分成两个节奏：首增量立即显示，后续短间隔合并，完整快照最多每秒一次并在终态强制落盘。
- 流式热路径只消费新增 delta 维护思考块和高度元数据，不重复解析完整累计文本；工具完整输出继续通过详情弹窗访问。
- OpenSkills 远程同步改为后台单飞；会话关键路径只读取已存在的本地副本。首次尚无副本时本轮显式不注入 OpenSkills，后台成功后供后续轮次使用。
- 不引入用户配置开关；固定节流值属于内部实现细节，并以行为测试约束首增量不等待定时窗口。

## 方案权衡

- 仅把 1 秒改成 33ms：改动最小，但会把当前全量解析和完整保存放大约 30 倍，拒绝采用。
- 缓存整个会话准备结果：首包最快，但技能、权限和指令失效边界复杂，可能返回陈旧或越权上下文，本轮不采用。
- 共享请求、增量状态、保存去抖和后台远程同步：修改边界较多但语义清晰，能分别控制主线程、渲染、IO 和会话预处理成本，采用此方案。

## 架构说明

- 桌面消息更新必须保持快速且无同步网络；`Task` 只承载后台工作，状态切换继续在 Iced 更新线程完成。
- 会话持久化保留现有按 session 协调和最终快照语义，不丢失取消、错误或完成前的最后增量。
- 技能发现继续遵守现有目录、插件和安全策略；只移动远程同步时机，不扩大技能可见范围。
- 所有任务线性执行，因为多个任务共享会话状态结构，并且仓库要求的全量 clippy 不能并发争用构建资源。

## 开发策略

- 对会改变行为的代码，使用失败验证-通过验证-重构。
- 在实施步骤前规划失败验证命令和预期失败。
- 将实施步骤限制在失败测试所证明的行为范围内。
- 测试真实行为，不验证模拟对象或实现细节。
- 每个任务完成前执行聚焦测试和 `cargo clippy --all-targets --all-features -- -D warnings`；不运行仓库禁止的全量测试、fmt check、wasm check 或 Makefile 命令。
