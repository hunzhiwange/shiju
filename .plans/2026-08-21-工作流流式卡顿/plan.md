# 工作流流式卡顿修复计划

目标：在不丢失工作流子会话输出和 SSE 恢复能力的前提下，显著降低 plan-run 流对 Iced 消息循环的唤醒频率，恢复动画与交互流畅度。

范围：仅调整桌面端 plan-run SSE 到 Iced 消息通道之间的增量转发与日志级别；保留现有会话状态层 50/100ms 合并、终态保存、子会话展示和网关协议。

范围外：不修改聊天消息渲染、动画样式、任务计划执行语义、网关 SSE 协议和当前工作区已有的聊天视觉改动。

假设：附件在约 63 秒内包含 400 个连续 `session_delta`，而当前 `gateway_agent_stream` 会为每个 delta 调用一次 `output.try_send`；状态层合并发生在 Iced 消息进入之后，无法减少 UI `update/view` 唤醒。

## 设计决策

- 选择在桌面订阅边界按 220ms 或 360 字符阈值合并同一子会话的 delta，使传输读取与 UI 刷新解耦，同时避免改变服务端及 CLI 行为。
- 不采用单纯放大状态层 100ms 窗口，因为原始 delta 仍会逐条进入 Iced 消息循环。
- 不丢弃增量；等待、完成、取消、错误及其它结构化事件前必须冲刷已缓存文本，成功转发后才推进可恢复流游标。
- `session_delta` 改为 debug 级别并记录合并后的长度；生命周期和终态事件继续保留 info 级别。

## 架构说明

- `gateway_agent_stream` 当前以容量 100 的 `iced::stream::channel` 向 UI 发送消息；新增的合并器位于 SSE 回调和该通道之间。
- 现有 `PlanRunSessionDelta`、`queue_agent_session_delta`、后台 100ms 状态合并和 1 秒保存防抖保持不变，避免与未提交的聊天渲染改动冲突。
- 合并器必须以 16KiB 为单批硬上限并触发冲刷，通道关闭或背压时沿用明确停止/恢复路径，不能以无限队列掩盖故障。

## 开发策略

- 对会改变行为的代码，使用失败验证-通过验证-重构。
- 在实施步骤前规划失败验证命令和预期失败。
- 将实施步骤限制在失败测试所证明的行为范围内。
- 测试真实行为，不验证模拟对象或实现细节。
