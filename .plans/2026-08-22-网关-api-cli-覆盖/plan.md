# 网关 API CLI 覆盖计划

目标：为安全且有用户或运维价值的 Gateway API 提供稳定、可脚本化的 `shiju api` 入口，并对 260 条路由逐项给出覆盖结论。

范围：新增远程 Gateway CLI 上下文、结构化输入输出、确认机制和按业务接口族组织的子命令；复用并补齐 `vw-gateway-client`；覆盖 JSON、文本、SSE 与 WebSocket 协议；建立路由到 CLI 的自动审计。

范围外：伪造第三方入站 webhook、把占位端点包装成可用能力、改变 Gateway API 语义、兼容重复 HTTP 别名、重构 TUI、处理当前 SHIJU 与桌面未提交改动。

假设：`bootstrap.rs::gateway_route_entries` 是当前 260 条路由的清单来源；CLI 已依赖 `vw-gateway-client` 与 `vw-agent`；多数业务域已有客户端封装，新增 CLI 应复用这些方法。

## 设计决策

- 选择 `shiju api <领域> <操作>` 的显式命名空间；顶层旧命令保持本地语义，不与远程 Gateway 操作混淆。
- 不采用仅暴露 method/path 的通用裸请求器：覆盖快但缺少类型、确认和安全边界；也不按单 URL 拆任务，避免碎片化。
- 一个任务覆盖一个内聚接口族；HTTP 方法别名和尾斜杠别名折叠为一个 CLI 操作，入站回调、占位接口保留明确不支持结论。

## 架构说明

- `vw-cli::handlers::api` 负责 clap 参数、租户/认证上下文、输入、输出和确认；业务 HTTP 只能经 `GatewayClient`。
- 默认输出 JSON，流式输出 JSONL；密钥只从环境变量、文件或 stdin 读取，破坏性与宿主副作用操作默认拒绝并要求 `--yes`。
- 任务线性执行，因为各接口族都需修改中央 `ApiCommands` 注册文件；不安排会争用同一文件的并行批次。

## 开发策略

- 对会改变行为的代码，使用失败验证-通过验证-重构。
- 在实施步骤前规划失败验证命令和预期失败。
- 将实施步骤限制在失败测试所证明的行为范围内。
- 测试真实行为，不验证模拟对象或实现细节。
- 每个代码任务运行聚焦测试及 `cargo clippy --all-targets --all-features -- -D warnings`；不运行全量 `cargo test`、fmt、wasm 或 Makefile 命令。

## 覆盖判定

- `CLI 已覆盖`：存在可解析命令、真实客户端调用、稳定输出和成功/错误测试。
- `协议别名`：重复方法或尾斜杠路由由同一命令覆盖，不新增重复命令。
- `明确排除`：第三方 webhook、内部生产者回调、运行时条件路由或占位能力，审计中必须带具体原因。
- 最终门槛：路由清单无未分类项；所有非别名、非排除的安全接口均映射到一个 CLI 操作。
