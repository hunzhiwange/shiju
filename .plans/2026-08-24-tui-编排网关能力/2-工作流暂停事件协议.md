## 上下文

- `WorkflowRunResponse.pause: Option<WorkflowPauseDto>` 已存在，但当前 `VibeWindowWorkflowFinishedData` 丢弃它，TUI 无法构造合法 `workflow_resume` 请求。
- 新事件/字段必须使用现有 `WorkflowPauseDto`，不得把 form token 写日志；旧无 pause SSE 保持兼容。
- client parser 未知事件仍走 `Unknown`，但服务端暂停必须成为明确强类型事件。

## 测试计划

- 行为：暂停的 Workflow SSE 含强类型 pause 数据，client 无损解析；普通完成事件不虚构 pause。
- 失败验证测试：新增 `workflow_sse_preserves_human_pause`、`workflow_client_parses_pause_event_without_logging_token`。
- 失败验证命令：`cargo clippy --all-targets --all-features -- -D warnings`
- 预期失败原因：服务端 finished 数据和 `GatewayWorkflowStreamEvent` 尚无 pause 表达。
- 通过验证命令：`cargo clippy --all-targets --all-features -- -D warnings`
- 模拟策略：使用真实 Workflow response/SSE 序列化和 client parser；不 mock 协议转换。

## 步骤

1. 为有 pause 和无 pause 两类响应添加失败测试。
2. 运行失败验证命令并确认 pause 在 SSE/client 边界丢失。
3. 最小扩展服务端事件和 client enum/parser，复用 `WorkflowPauseDto`。
4. 确认日志与错误格式不包含 form token，旧事件仍能解析。
5. 运行通过验证命令并审查协议差异。

## 验证

- 运行：`cargo clippy --all-targets --all-features -- -D warnings`
- 预期：退出码 0；新增跨 crate 测试编译；无 warning。
- 所需证据：失败显示 pause 丢失、通过退出码、序列化 JSON 与强类型解析保留字段、日志无 token。
