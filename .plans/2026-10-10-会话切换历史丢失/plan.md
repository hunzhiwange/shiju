# 会话切换历史保护与长会话性能计划

目标：切换运行或已结束的会话均保留完整历史，并降低长对话与轨迹的交互卡顿。

范围：桌面冷打开历史交接、网关完整读取、UI 内容保存并发保护、运行中切换的缓存与流事件交接，以及长消息和轨迹重绘成本。保留显式重置、复制、搜索、折叠和原始载荷查看语义。

范围外：聊天样式、会话列表首次加载 SQL、历史格式迁移、重品牌和全量测试。旧 `.plans/2026-10-10-长会话列表卡顿/` 的同路径消息视图任务与本计划二选一，不并行执行。

假设：桌面端为报告的入口。用户观察到运行中切换后对话内容缺失、轨迹仍在；具体丢失范围尚未确认。源码显示一条可达的运行中缓存缺口，仍须用回归测试确认它解释现场现象。

## 原因分析

- `open.rs` 冷打开先装入 UI Store，随后 `SessionOpenPrepared::RemoteHistory` 直接调用 `apply_prepared_session_open`。该分支未执行旧 `SessionMessagesLoaded` 已有的“较短网关历史保留缓存”判断；较短结果可替换完整聊天。热缓存命中时不会走这条路径，符合“偶发”。
- 网关 `message::messages` 对读失败的单条消息直接跳过并返回成功；不指定 `limit` 也可能得到缺项的历史。此为可能的短结果来源，尚未证实是用户现场的实际来源。
- `session_ui_save` 最终调用 `replace_session_messages`，先删除同会话全部 UI 消息再插入传入快照。若前端已接纳缺项结果，或过期保存晚到，缺失可能由界面现象变成持久化损失。
- 活跃流增量在 `finish_active_stream_tail_update` 清除普通聊天缓存；切走时 `stash_active_session_view` 成功写入热缓存后不会补普通缓存。下一条后台增量从空普通缓存续写，并按内容签名使热缓存失效，可能丢掉此前对话。若恰好结束而无后台增量，终态保存也可能从缺失的普通缓存恢复。
- 轨迹视图每次构建重新运行 `project_trajectory`，投影过程中重复复制累积消息；重复步骤索引检测还对每个键全量扫描。长助手消息虽按消息虚拟化，可见的一条长消息仍反复解析工具 JSON、复制文本。既有 5 秒进程采样中，主线程热点集中在 `chat_panel::message_view`，轨迹卡顿目前只有源码证据，需补实测。

## 设计决策

- 桌面刷新可选“按长度保留”或“按消息 ID 比对”。选择 ID 比对并保守保留已确认的历史；单纯长度不能区分新尾部、内容更新与显式重置。
- 网关可继续跳过坏记录或将完整读取失败显式报错。选择完整读取显式失败，让桌面保留 UI Store 历史；有限列表的原有语义需由聚焦测试确认。
- 保存可仅依赖桌面缓存或在持久化事务内拒绝过期快照。选择持久化事务校验；显式重置必须保留可验证的缩短路径。
- 运行会话优先在切走时保证普通缓存有完整续写基线；也可从热缓存读取，但需避免后台事件修改被随后热恢复覆盖。用切换、后台增量、终态和重进会话的行为测试选择最小方案。
- 轨迹优先复用未变的投影，再优化投影内部重复扫描；消息视图使用已有渲染缓存，不扩大持久化结构。性能结论必须来自相同输入的前后测量。

## 架构说明

- 桌面入口是 `OpenProjectSessionPressed`；`SessionOpenPrepared` 以会话 ID 和打开代次筛除旧异步结果。UI Store、网关消息使用不同存储，必须按消息 ID 判断交集。
- 桌面保存经 `session_gateway.rs`、`ui_ops.rs` 到 `SessionStore::save_session_ui_content`；SQLite、PostgreSQL 都整批替换消息。当前工作树存在大量其他改动，实施时只修改任务所列文件。
- 运行中会话热缓存位于 `session/view_cache.rs`，普通缓存与其失效边界位于 `session/active.rs`；后台流在 `message/chat/stream/stream_events.rs` 更新普通缓存。
- `trajectory::view` 直接投影步骤与原始载荷；长消息使用 `ChatRenderCacheEntry`，需要按内容与显示选项保持失效规则。

## 开发策略

- 对行为变更先写失败测试，再做最小实现和通过验证。
- 用 `cargo nextest run` 运行聚焦用例；代码任务均执行 `cargo clippy --all-targets --all-features -- -D warnings`。不运行仓库禁止的全量测试、格式检查或 Makefile 命令。
- 每个任务仅凭当次失败与通过证据完成；若既有改动导致构建失败，记录阻塞，不处理无关代码。
- 性能改动先记录场景与基线，复用现有语义测试，再对同一工作负载复测；不以易抖动的单次毫秒阈值作为单测断言。
