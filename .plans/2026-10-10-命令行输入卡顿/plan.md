# 命令行输入卡顿计划

目标：消除长会话与流式输出期间命令行输入偶发积压，使连续打字及时显示且不饿死后台事件。

范围：调整 `vw-cli` TUI 主循环的输入、流消息和绘制调度；减少 `vw-tui` 聊天记录在每次输入重绘时的全量复制与重复测量；使用 RustCodeGraph 核对调用影响，完成聚焦回归后提交本计划变更。

范围外：不修改 Gateway 协议、模型流内容、桌面 Iced 输入框、Zed 或终端模拟器，也不引入新配置和性能依赖。

假设：卡顿指 `shiju` 交互 TUI 的输入回显延迟。当前主循环每轮先无上限清空流消息、完整绘制，再只读取一个终端事件；记录渲染每帧还会克隆全部缓存行，因此成本会随流量和会话长度增长。

## 设计决策

- 方案一仅缩短 50ms poll：无法解决事件已就绪时的主线程工作积压，不采用。
- 方案二为输入单独开线程：会扩大终端生命周期和同步边界，不采用。
- 采用单线程公平调度：输入和流事件均设每轮预算、批量应用输入后只绘制一次；同时让记录渲染只物化当前视口所需内容。
- Rust 任务先用 `./skills/rustcodegraph/SKILL.md` 验证符号、调用方与影响范围；所有验证完成后再由独立任务使用 `./skills/git-commit/SKILL.md` 提交，避免并行会话争用 Git 索引。

## 架构说明

- `vw-cli/src/cli/tui/app.rs` 继续拥有终端生命周期和事件循环；`ActiveRunner` 继续拥有 Gateway/宿主通道。
- `vw-tui` 只优化纯渲染状态，不引入 Gateway 语义；保持鼠标选择、滚动与快照布局不变。
- Git 提交仅包含本计划的代码、测试及保留的计划文档；现有无关工作区改动必须排除。

## 开发策略

- 对会改变行为的代码，使用失败验证-通过验证-重构。
- 在实施步骤前规划失败验证命令和预期失败。
- 将实施步骤限制在失败测试所证明的行为范围内。
- 测试真实行为，不验证模拟对象或实现细节。
