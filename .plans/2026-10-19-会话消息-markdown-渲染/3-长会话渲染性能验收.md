## Cargo 共享槽位规则

1. 同一仓库的所有计划和任务共用仓库根目录下的 `target/rust-slot-1` 至 `target/rust-slot-10`，不得为任务、会话或计划另建构建目录，也不得按任务编号取模固定分配。
2. 每次构建/验证阶段开始前，创建仓库根目录下的 `target/rust-slot-locks`；依次用原子命令 `mkdir target/rust-slot-locks/slot-N.lock` 尝试领取槽位，`N` 为 1–10。仅 `mkdir` 成功者获得该槽位；这些相对路径命令从仓库根目录执行。
3. 领取成功后，在自己的锁目录中记录计划、任务、会话标识和持有进程 PID。同一槽位同时只允许一个持有者；已占用时尝试下一个，仅全部 10 个槽位都占用时等待并重试。
4. 将 `CARGO_TARGET_DIR` 设置为领取槽位的绝对路径，例如领取槽位 3 后，从仓库根目录执行 `export CARGO_TARGET_DIR="$PWD/target/rust-slot-3"`。示例编号不代表固定分配。
5. 所有 Cargo 构建、检查、测试以及调用 Cargo 的脚本和子进程均继承该设置，不得通过 `--target-dir` 或其他配置绕过槽位；生成的二进制也从该槽位定位。
6. 该阶段的 Cargo、脚本以及使用槽位产物的子进程全部结束后，删除自己写入的占用记录，并用 `rmdir` 释放自己的锁目录；保留槽位编译缓存供后续任务复用。
7. 正常结束、失败和中断均须清理自己的锁；在后台进程或其他使用槽位产物的进程仍运行时不得提前释放。规划清理步骤时覆盖这三种退出路径。
8. 遗留锁须先核实持有会话及相关进程已结束；无法确认则保持占用，不得删除其他活跃任务的锁、进程或缓存。
9. 生成或更新计划时，统一移除与这些规则冲突的单一 Rust 共享构建空间、逐任务独立目录和 Cargo 缓存全局独占窗口要求；仍须遵守源码文件占用、真实业务依赖和其他共享验证资源的互斥，不能仅因缓存分槽就把任务判定为可并行。
10. 最终验证记录包含实际槽位、绝对路径 `CARGO_TARGET_DIR`、确切命令、退出码和有效测试数量；Rust 代码修改后先运行 `cargo fmt --all`，再运行相应验证。编译成功或零测试不能替代行为验收证据。

## 测试计划

- 行为：重复查看同一完成态消息不重解析或重建编辑器；离屏消息缓存按现有窗口规则清理；长回复与密集列表保持可用响应，流式输出不持续重建完成态 Markdown 树。
- 失败验证测试：在 `chat_ui_tests.rs` 增加 `markdown_cache_reuses_unchanged_message`、`markdown_cache_prunes_offscreen_blocks`；在 `markdown_tests.rs` 增加 `long_markdown_keeps_bounded_editor_work`，根据实测缺口只保留能证明真实缓存边界的测试。
- 失败验证命令：`cargo test -p vw-desktop --lib markdown_cache_reuses_unchanged_message`；`cargo test -p vw-desktop --lib markdown_cache_prunes_offscreen_blocks`。先用 `cargo test -p vw-desktop --lib -- --list` 确认过滤命中非零测试。
- 预期失败原因：若任务 1、2 已保留缓存边界，测试可能直接通过，此时将其记为防回归证据；若出现重复建树或离屏缓存未回收，测试须先失败再做最小修复。
- 通过验证命令：`cargo test -p vw-desktop --lib markdown_cache_`；`cargo test -p vw-desktop --lib long_markdown_keeps_bounded_editor_work`；`cargo clippy --all-targets --all-features -- -D warnings`。
- 模拟策略：真实 `App`、消息缓存与虚拟窗口；不 mock 文本长度、块数量或清理逻辑。耗时和界面流畅度通过同机实际运行观察，避免将不稳定时钟阈值写入普通单元测试。

## 步骤

1. 准备可重复的 1 万字混合正文、200 项列表/代码块与 500 条历史消息场景；记录机器、构建模式、消息规模及原始编辑器路径的基线。可以使用独立临时检出观察旧路径，不能改动其他任务的工作树。
2. 检查 Markdown 解析和编辑器创建只发生在消息更新/缓存准备阶段，视图构建仅借用缓存；长文本不会按每一行无限创建控件。
3. 编写缓存复用、离屏清理及长文本边界测试；若本次改动使测试失败，做最小修复。
4. 用相同场景在改动前后各重复三次，记录长回复首次显示、历史滚动与内存占用；出现可复现的明显卡顿或持续增长时定位并修复，再复测。
5. 运行聚焦测试及 Clippy，检查修复未改变任务 2 的复制行为。
