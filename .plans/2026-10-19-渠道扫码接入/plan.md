# 五渠道扫码接入计划

目标：将 QwenPaw 的钉钉、飞书、企业微信、QQ、微信扫码授权流程移植到 VibeWindow，并让授权结果可用于实际消息通道。

范围：五个去重渠道的二维码获取、状态轮询、失败与过期处理、凭证安全写入和桌面设置界面；补齐企业微信与微信基础文字消息收发。复用已有钉钉、飞书、QQ 通道，不替换其现有接收模式。

范围外：迁移 QwenPaw 的全部媒体、卡片、语音和历史数据；已有配置数据迁移；新增云端托管服务或跨平台二维码扫描器。扫码由用户手机端完成。

假设：请求中的“支持扫描”指手机扫码授权。QwenPaw 的 `qrcode_auth_handler.py` 明确注册五个渠道；VibeWindow 已有钉钉、飞书、QQ 通道，尚无企业微信和微信通道。

## 设计决策

- 采用现有网关、GatewayClient 和 Iced 设置页路径，保持渠道身份与凭证保存边界。其他方案是桌面直连平台或直接嵌入 QwenPaw Python 运行时；前者重复网络/安全逻辑，后者破坏 Rust 优先架构。
- 只复用来源协议和状态语义，不机械复制 Python SDK。企业微信的 WebSocket 帧、鉴权和回包须由来源 SDK/测试核实后实现；无法验证的能力明确报错。
- 授权先返回可显示的二维码与不含长期凭证的轮询句柄；仅确认后交给现有配置保存机制。错误与日志不得包含密钥、二维码原始内容或轮询句柄。

## 架构说明

- 配置位于 `vw-config-types::channels`；通道 trait 与工厂位于 `vw-agent::channels`；受认证网关路由在 `gateway/api/handlers`；桌面配置使用 `vw-gateway-client` 与 `system_settings_channels`。
- 扫码端点必须受网关认证、租户隔离和渠道白名单限制；固定平台主机、防止任意 URL 请求；微信返回的 `baseurl` 需限制到可信目标；授权状态仅在确认时返回凭证。

## 开发策略

- 每个行为变更先写失败测试并运行，再做最小实现，通过聚焦测试后运行仓库要求的 Clippy。
- 任务按批次执行：批次 1 建立授权契约；批次 2 的钉钉、飞书、QQ 可并行；批次 3、4 分别完成企业微信、微信；批次 5 补其扫码协议；批次 6 完成桌面流程；批次 7 做端到端回归。
- 并行只限批次 2：三个任务写入不同的提供者文件和测试文件，且分别领取 Cargo 槽位。
