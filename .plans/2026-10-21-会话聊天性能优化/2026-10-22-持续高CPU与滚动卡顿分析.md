### 1. 输入框的小徽标，触发全局会话和历史消息扫描（P0，调用栈与源码一致）

调用入口 `crates/vw-desktop/src/app/components/input_panel/mod.rs:734`：每次 view 无条件调用 `running_agent_sessions(app)`，算完才决定是否显示徽标。弹层关闭不会跳过计算。

`components/input_panel/agent_sessions.rs` 的实际工作：

- `195`：只检查 active_session_id 是否存在，不要求当前正在生成。因此打开已有会话就进入此路径。
- `64`：合并当前列表和所有项目会话，重新建立 HashSet 去重。
- `83`：遍历当前全部已加载消息和所有已缓存会话的消息，重新解析计划运行控制信息。
- `73`、`126`：为父会话及递归访问的子会话复制整份 ChatMessage 列表和正文。
- `127`：每次递归调用 `session/agent_children.rs:186`，其 `197` 又重新构建全局会话 ID HashMap，再扫描消息中的工具载荷。
- `147`：每层再遍历全部会话找计划运行后代；`152` 为读取 is_requesting 取得 owned runtime，存在额外深复制。

`session/agent_children.rs:143` 先解析工具 JSON，`151` 才判断是不是 workflow_node，其他工具的大载荷也会付出解析成本。

**影响：** 成本取决于全局已知会话、已缓存历史正文和子树大小，而非当前屏幕显示几条消息。即使最后结果是“没有运行中子任务”，前面的汇总、扫描和复制也已经完成。这解释了为什么打开一个短会话也可能卡，以及流式每次刷新会把成本放大。

**修复方向：** 会话列表更新时维护 ID/parent 索引；消息或工具状态改变时更新对应会话的子任务摘要；view 只读取已有徽标计数和当前树的摘要。递归共用索引，正文使用借用，不在 view 扫描所有缓存会话。弹层内容延迟到打开时构建，但徽标必须继续准确更新，不能简单隐藏功能。

### 2. 左侧会话栏存在二次复杂度筛选，且 view 同步读文件（P0/P1，侧栏调用栈与源码一致）

`views/project/layout/work_sidebar.rs:1503` 每次 view 重算 model：

- `146–170`：collect_top_level_sessions 外层遍历会话，内层 `sessions.iter().any(...)` 查父会话，符合条件的子会话多时最坏 O(N²)。
- `285`：先全局计算任务列表；`321`：随后逐项目再次进行同类筛选。
- `300`、`349`：显示条数限制在上述筛选之后执行，所以“只展示几十条”没有约束全量筛选成本。
- `277–283` → `208–229`：每次重建时收集项目并加载置顶数据。`crates/vw-shared/src/session/ui_store.rs:34–40` 实际执行 exists、同步文件读取和 JSON 解析。这是明确的 UI 主线程 I/O；尚未单独测量它在本次侧栏样本中的占比。
- 即使只选“任务”标签，model 仍计算空间列表；空间折叠时也先筛选全部会话以计算总数。

**修复方向：** 以 (path, project_id, session_id) 建索引保留原有匹配语义，把父会话查找改成索引查询；置顶数据在加载/置顶变更时更新内存状态；任务和空间摘要在列表或筛选条件变化时重算，鼠标移动和正文增量不应重算全部侧栏数据。

### 3. 全局事件把这些昂贵计算反复触发（放大器，源码确认）

`impls/app_subscription.rs:30` 无条件把 CursorMoved 转成应用 Message。`chat_panel/mod.rs:528` 将滚动转为 Message。当前依赖 iced_winit 0.14.0 的 `src/lib.rs:1214` 在应用消息非空时重新 build_user_interfaces；update 最后返回 Task::none 仍不能阻止这次 view 重建。

此外，预览打开时有 33 ms LSP tick，宠物窗口存在或探索动画活跃时有 90 ms 活动 tick。它们是条件性触发源，不代表用户当前一定开启了这些功能。

因此真实放大链是：鼠标/滚动/流式事件 → 整体 view → 输入框全局会话扫描 + 侧栏全局筛选 → 主线程交互延迟。应同时去掉无关的全局刷新触发、把昂贵的数据派生移出 view。只延长流式定时器不能解决静态会话的这一问题。

### 4. 文本布局仍有风险，但优先级应服从这次样本

单条长回复仍用整体只读编辑器：`message_view/markdown.rs:451–452` 为 Shrink 和大 max_height。底层 iced_widget 0.14.2 `text_editor.rs:621` 调用 editor.update，Shrink 再调用 min_bounds；iced_graphics 0.14.0 `text.rs:202` 遍历 layout_runs 测高。已有缓存可以避免部分重复整形，因此不能笼统宣称每次都完整重新整形；但消息级虚拟化仍不保证单条长消息内部的工作量有界。缓存失效、重建编辑器和全文派生问题见后面的初次审计。

### 验收顺序

1. 先修输入框投影和侧栏：空会话/短会话/长会话各测，分别增加全局历史会话数量、已缓存历史消息、运行后代数量；无相关状态变化时重复 view 不再扫描全局历史或读文件。
2. 同一会话对比侧栏展开/折叠、鼠标静止/移动/滚动、生成停止/进行中，记录真实主线程 view+layout 帧耗时和 CPU。
3. 再依据剩余热点决定正文块级虚拟化。性能测试必须覆盖 input_panel 和 work_sidebar，不能只检查 chat_panel 的挂载行数与克隆计数。

## 结论

前一轮优化解决了部分历史加载、流式合并和消息存储问题，但没有完成“实际 UI 帧工作量有界”的目标。消息级虚拟列表限制了挂载消息数量，没有限制消息内部文本的布局量；revision 缓存限制了部分解析，没有阻止全窗口视图重建、附件全文复制和编辑器重新创建。后台另有一条正常执行路径仍保存完整会话，绕过了新增的消息 delta。

## 问题与修复方向

### 1. 后台记录一次 AI 调用，仍读取并保存完整会话（P0，实测热点）

证据：

- `crates/vw-agent/src/session/processor/artifacts.rs:98`：每步构造调用载荷，并在第 137 行调用持久化。
- `crates/vw-agent/src/session/ui_store.rs:1326`：`load_session_scoped` 读取完整会话，修改 `calls` 后调用 `save_session_scoped`。
- `crates/vw-agent/src/session/store/postgres.rs:304`：完整保存依次替换 messages、calls、steps。
- 同文件第 1313 行：删除当前会话所有 calls，遍历历史 payload，逐条 JSON 序列化和 INSERT。

因此，即使 Desktop 已改用消息 delta，正常 Agent 执行仍能触发完整历史重写。长历史、大调用载荷会放大 JSON 序列化、数据库往返和事务成本；这也可能与并发 UI 写入形成旧快照覆盖风险，需要并发测试确认。

修复：在存储层增加真正的单调用 upsert/append 原语；按现有 stream_id 更新语义处理非零 stream，零 stream 保持追加。事务内更新必要的 call_count/updated_ms，不加载 messages/steps，不重写其他 calls。SQLite/PostgreSQL 同步实现；并发追加序号和幂等性必须有明确约束，不能以无锁 MAX(seq_no)+1 代替。保留完整保存给显式快照操作。

验收：预置大量历史 calls 后更新一条，SQL 写入行数、序列化字节仅与本条 payload 有关；不删除历史 calls，不修改 messages/steps；覆盖相同 stream 更新、零 stream 追加、并发调用及并发消息 delta。

### 2. 高频鼠标和滚动消息触发整窗口 view/layout（P1，源码确认）

证据：

- `crates/vw-desktop/src/app/impls/app_subscription.rs:24`：每个 CursorMoved 都发布全局 PointerMoved。
- `crates/vw-desktop/src/app/message/view/layout.rs:124`：普通移动也进入 App 更新；没有拖拽时通常只记录坐标。
- `crates/vw-desktop/src/app/components/chat_panel/mod.rs:528`：scrollable 每次回调发布 ScrollChanged。
- `crates/vw-desktop/src/app/message/chat/input.rs:284`：窗口内滚动虽跳过部分测量任务，但 App 消息已经产生。
- 本机 `iced_winit-0.14.0/src/lib.rs:1214`：消息非空就调用 update 后重建窗口 interfaces；`iced_runtime-0.14.0/src/user_interface.rs:93` 的 build 调用 root.layout。

`Task::none()` 只是没有后续任务，不代表 Iced 跳过本次 view/layout。现有 RevisionRenderKey 也不是 widget/layout 缓存。

修复：普通鼠标位置优先留在 widget 事件层，拖拽和实际需要坐标的动作才向 App 发消息；先审计所有 cursor_position 消费者，不能直接删除全局追踪。滚动偏移由滚动控件持有，在跨可视/预加载区间、翻页阈值、尾随状态或导航状态改变时通知 App；必要时按帧合并最新偏移，并保留滚动结束的最终状态。稳定消息子树按身份、revision、宽度及交互状态复用。

验收：同一可视窗口内滚动时正文 view/layout 次数明显下降；仍正确处理回到底部、向上翻页、拖拽、选择、右键定位、工具展开和高度变化。

### 3. 消息级虚拟化没有控制文本内部布局量（P1，源码确认，耗时待测）

证据：

- `chat_panel/mod.rs:472`：虚拟化单位是一整条消息。
- `message_view/markdown.rs:554`：正文合成为单个只读编辑器；第 451 行为 Shrink 高度。
- `chat_panel/tool_text_support.rs:196`：编辑器最大高度为 1,000,000 px。
- 本机 iced_widget 的 TextEditor::layout 会调用 editor.update 和 min_bounds；iced_graphics 的 min_bounds 通过 layout_runs 计算文本尺寸。
- 编辑器有 20,000 字符和单行 2,000 字符安全限制，超过限制会进入静态文本兜底；这并没有形成统一的可视区字节/行预算。

这不能被描述为“每帧一定重新整形全文”：底层有缓存。但宽高变化、缓存重建会触发布局，测量也需要遍历已布局文本；整条消息挂载时，屏外正文仍可能参与这些工作。静态文本兜底同样需要布局。

修复：长回复按稳定文本块或段落建立内部高度索引，只布局视口及少量缓冲块；不改变全文复制和连续选区语义。已完成块保留布局，活动尾单独更新。只把文本切成多个控件但全部挂载，仍不算内部虚拟化。中文、超长单行、代码围栏及跨块选区须走真实渲染验证。

### 4. revision 命中后仍然逐帧扫描并复制正文（P1，源码确认）

`message_view.rs:316` 无条件调用 `parse_attachment_markers(content)`。后者在 `input_panel/attachment.rs:334` 分配正文大小的 String，扫描标记，再逐行 trim、collect、join 并生成新 String。即使消息无附件且 revision 未变，也要支付这笔成本。Markdown 编辑器缺失时，`markdown.rs:569` 还会调用 `markdown_editor_text(blocks)` 重建全文显示串。

修复：把附件结构、清理后的显示文本、Markdown 兜底文本纳入消息 revision 派生结果；view 仅借用。无标记快路径使用借用时，注意保留当前 trim/换行规范化语义，不以行为变化换性能。流式路径必须增量处理或限定活动尾，不能只是把全文工作换一个函数名。

验收：同 revision 重复 view、滚动、悬停不扫描正文、不分配正文大小的字符串；实际计数应覆盖附件处理和兜底路径。

### 5. 分块结果落到主线程时，缓存先被清空，复用判断失效（P1，源码确认）

`session/chat_ui.rs:1018` 和第 1022 行先删除整个 chunk 的 Markdown blocks/editors，第 1060 行才检查旧块是否存在以决定 reuse_markdown_cache。该 chunk 内的旧块已删，复用条件无法成立。随后第 1065–1073 行重复 clone render_entry，重新构造辅助编辑器和正文 Content。`sync_markdown_blocks_for_text:365` 中 Markdown 解析及编辑器创建也发生在应用结果阶段。

因此“后台预热”没有把全部昂贵工作移出主线程，滚动跨 chunk 时仍可能突发卡顿。

修复：先按稳定 entry key/revision 比较，未变条目直接保留；仅替换变更或缺失条目，移动结果所有权减少 clone。Markdown 解析放到纯数据准备阶段；编辑器初始化按实际可视需求和每帧工作预算调度。避免一次性创建整块不可见编辑器。

验收：重复应用相同 revision 保持编辑器及选择状态；跨 chunk 时记录主线程 apply 耗时和创建编辑器数；过期结果不覆盖更新后的消息。

### 6. 测量点更新后，兼容高度索引仍被全量重建（P1，源码确认）

`message/chat/input.rs:779` 更新单条高度后，第 784 行调用 `sync_chat_virtualizer_compat_fields`。该函数在 `session/chat_ui.rs:480` 复制全部已加载高度，再调用 `chat_height_index.set_heights`；`height_index.rs:81` 重新分配并构建 Fenwick 树。

现有流式估计路径已有 point update 快路径，但实际测量回执没有贯穿同一约束。代价与已加载消息数有关，不是数据库历史总数。

修复：明确唯一高度状态所有者；必须保留兼容索引时，测量也同步点更新，结构变化才重建。测试不能只统计 ChatVirtualizer 内部的重建次数，还要统计兼容索引。

### 7. 预热/淘汰调度仍为读取一个 bool 克隆运行态（P2，源码确认）

`session/chat_ui.rs:538` 的 `current_session_runtime().is_requesting` 返回 owned SessionRuntimeState；`session/runtime.rs:64` 直接 cloned。调用者 `chat_chunk_schedule_input` 被缓存淘汰、预加载路径使用，滚动跨可见区间会进入这些路径。底层 iced text_editor::Content 的 Clone 会调用 text() 并重新创建 Content，并非共享引用。

修复：改为 current_session_runtime_ref 的借用查询，检查同类只读调用。验收覆盖真实 ScrollChanged、预热和淘汰链路，要求 runtime clone 为零。

### 8. 现有性能验收未覆盖真实瓶颈（P0，验证缺口）

`chat_panel/performance_tests.rs`：

- 第 47 行的长会话测试主要操作 timeline 和虚拟高度模型，不能证明实际绘制帧有界。
- 第 151 行 persistence 测试 reset 后直接断言计数为零，没有执行持久化操作。

这些测试可以验证局部数据约束，但不能作为 UI 流畅或后台无全量保存的证据。任务完成状态与真实性能验收之间存在缺口。

## 推荐实施顺序

1. **建立可复现运行基线**：确认前台/后台 PID、二进制版本、debug/release、渲染后端；分别录制空闲、打开长会话、持续滚动、流式生成和后台生成。记录主线程帧耗时 p50/p95/p99、超过 50 ms 的停顿、进程 CPU 与内存。禁止把所有线程的等待样本当成 CPU 热点。
2. **先消除已确认且改动可控的成本**：单调用增量持久化独立提交；运行态借用、兼容高度点更新、chunk 复用分别提交和验证。这几项都有明确源码证据，其中持久化还有运行采样证据。
3. **收紧 view 与事件路径**：去掉每次 view 的正文处理；减少无状态变化的全局 PointerMoved 和 ScrollChanged 发布；保留交互语义并做真实滚动对照。
4. **按帧热点决定内部虚拟化实现**：如果 TextEditor/layout 仍占主导，再做块级虚拟化及布局复用。不要继续只增加缓存数量或延长定时器。
5. **补端到端验收**：使用真实分布的长中文回复、工具卡、代码、历史分页和流式更新；测试实际存储操作、App 更新、layout/draw。验收包含空闲恢复、选区复制、主题、宽度变化、旧页锚点及终态内容。

建议目标需在相同机器、构建及数据下验收：60 Hz 场景 p95 帧耗时不超过约 16.7 ms；空闲停止无意义的周期性整树工作；单条调用保存成本不随历史 calls 增长；滚动窗口内无全文派生处理。以上是后续验收目标，不是本次已经达到的结果。

初次分析仅新增文档；后续代码修复和验证见下节。


## 发送消息后的追加修复与验证

本轮仅修改桌面流式更新路径：

- 请求代次与预热保护查询改为借用 SessionRuntimeState，避免复制输入编辑器、流式状态和待保存记录；克隆计数移动到实际 getter，避免漏计。

验证：流式事件模块 65 项聚焦测试全部通过，涵盖中文、工具替换、保存确认后继续追加、滚动及保存语义；Clippy 全目标全特性通过；桌面 debug 二进制构建成功。依赖 block 0.1.6 有既有 future-incompatibility 提示。
