# CC能力完整融合计划

目标：完整吸收 CC Switch 的产品能力，形成独立 Rust 业务包、统一网关 API 与原生桌面客户端，并在最终验收后收敛重复实现。

范围：完整后端源包、全部应用与账号、供应商/模型/配置、路由与聚合、高可用、额度/用量、MCP/技能/插件/规则、会话/工作区/记忆、项目组合、迁入备份同步、TS 业务原生化、桌面与系统集成、跨平台交付及最终去重。

范围外：本轮不执行复制、编码、用户数据迁移或发布；不绕过上游登录/权益限制；不修改数据网关 Go 仓库。本轮只交付大块能力需求，具体小需求在后续逐块拆分。

假设：源代码固定为本目录来源清单记录的提交和工作区快照；识矩已有网关、API 类型、客户端 SDK、ACP、模型 relay、安装与技能体系。现有能力不等于所有平台均已验收。

## 设计决策

- 选择整包保留后逐块融合；即时全量去耦风险高，长期双系统成本高，均不采用。
- 后端统一放 crates/vw-agent-apps；先保留 upstream/src-tauri，再建设原生 src。最终按等价证据去重。

## 架构说明

- API 类型 → 客户端 SDK；网关 → 独立业务包 → 执行主机资源，桌面只调用 API。
- 复用现有数据/权限体系，区分租户、项目、主机和账号；现有会话 relay 不扩权为公共代理。

## 开发策略

- 这是能力母计划，用户明确要求本轮不细拆。编号文件是完整能力边界，不能默认一个会话整块实现；后续用 create-task-plans 分解到可验证小需求。
- 首项为完整源代码引入，保持来源不变、完整可核对；不在第一项混入功能移植或去重。本轮只规划，未执行第一项。
- 源码许可保留；原始品牌和发布源不能变成识矩运行配置。未跟踪文件、编译产物和用户凭据不随代码搬迁。
- 对改变行为的小需求先失败验证再通过验证；使用真实配置/存储/进程/API 链路，外部不可控上游可替代并说明边界。完整性复制以哈希与清单验收，测试驱动开发不适用。
- API/执行端/SDK/Iced 形成每块能力的完整闭环；TS 校验、元数据、价格、同步调度等业务规则必须进入 Rust，不能只改 IPC 调用或换 UI。
- 能力覆盖、来源索引、批次、依赖和拆分入口分别在能力覆盖.md、来源清单.json、编号文件及 prompt.md。plan.md 是生成后只读的架构参考，不维护进度。
- 所有编号母任务初始未开始；仅生成子计划不能将整块能力标为已完成。完成需要全部子需求及实际行为证据。证据与阻塞只在对应任务及子计划记录。
- 源模块主责索引只是防遗漏入口，不能代替逐命令、逐事件、逐页面的语义核对。交叉能力需要在子计划明确唯一实现所有者，不增加长期双写。
- 母任务批次用于盘点与细拆，实施按子计划的直接产物依赖启动。同批独立任务并行，公共入口合入按执行分线协调。
- Rust 修改后 cargo fmt --all，再运行聚焦测试及 cargo clippy --all-targets --all-features -- -D warnings；不运行无过滤全量测试、wasm 检查或 Makefile。Cargo 使用各任务规定的共享槽位。
- 当前工作区已有其他计划与未提交实现，后续必须重新检查；不覆盖、提交或修复无关变更。现有 ACP 模型来源/技能挂载与动态工具计划继续拥有各自实现边界，母计划只在 API 接口与最终回归处衔接。

实机验收由用户按`.plans/2026-11-05-CC能力完整融合/人工验收.md`人工完成。自动任务以聚焦测试、隔离夹具和命令输出为证据，无需启动真实桌面、使用真实账号、截图或录屏。
