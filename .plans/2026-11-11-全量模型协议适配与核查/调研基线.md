# 调研基线与实施约定

## 当前证据

- `api.json`有230家供应商、8909条模型记录，`shiju.json`有1家供应商、40条模型记录，合计231家、8949条。原始文件SHA-256、各组供应商和数量见`目录基线.json`。
- `api.json`的230家供应商全部使用`npm`，其中191家是`@ai-sdk/openai-compatible`，8家是`@ai-sdk/anthropic`。25家未显式给出供应商API地址，必须核查SDK默认入口或部署参数。
- 840条模型声明`provider`覆盖，其中618条含`api`，508条含`npm`，103条含`shape`。`crates/vw-shared/src/provider/models.rs`当前仅以`adapter`表达供应商及模型覆盖，模型覆盖未保存这些API与shape字段；`state.rs::from_models_dev_model`当前使用供应商API。
- `models.rs::parse_models_text`直接反序列化，`merge_bundled_shiju`只覆盖`shiju`供应商。新供应商协议证据需有明确合并入口，不能假设把任意供应商写入shiju.json就会生效。
- `model_relay/transport.rs`已有Chat、Messages、Responses、Gemini入口，DeepSeek及阿里原生Messages选择含已验证专用分支。`generation.rs`已开始共用端点与认证原语，当前仍有相关未提交工作。
- `ad11da443`已修复关闭思考的Messages→Chat转换；有意保留对无法表示的非空思考状态的拒绝。本计划包含转换思考回放与流式能力任务，成功标准覆盖真实工具续轮。
- 现有`.plans/2026-11-05-常驻路由与完整协议适配/`及`.plans/2026-11-05-故障转移连通检测与诊断/`存在共享传输、转换和诊断任务。执行时检查实际源码和交付状态，复用已经交付的同职责实现，并在自己的任务中记录映射。

## 官方依据种子

- Models.dev公开数据与维护方式参见[官方仓库](https://github.com/anomalyco/models.dev)。目录的SDK标识和模型能力需保留；多协议端点支持仍按具体部署核查。
- 阿里明确区分OpenAI与Anthropic端点以及Token Plan、Coding Plan和按量服务。[官方接入指南](https://help.aliyun.com/en/model-studio/more-tools)
- DeepSeek明确提供Anthropic接口，并给出思考、工具和模型限制。[官方兼容说明](https://api-docs.deepseek.com/guides/anthropic_api/)
- Gemini提供OpenAI兼容入口，模型的思考关闭能力存在差异。[官方兼容说明](https://ai.google.dev/gemini-api/docs/openai)

以上链接为查询起点，查询任务必须记录执行当日核查日期和实际支持范围。

## 数据与验证合同

- 来源行身份为`来源文件、供应商ID、模型key`。部署身份保留供应商、模型API ID、地域/套餐和端点，`canonical_model_id`仅作来源关联。分组查询可以共享证据，但每条模型记录均须落到明确结论。
- 研究报告记录供应商与模型范围、请求协议、官方端点、认证方式、必要部署参数、文本/工具/思考/媒体/流式/结构化输出限制、来源URL、核查日期、证据摘录及结论。结论使用“官方确认、实测通过、明确不支持、资料不足、不适用于文本ACP、缺少凭据、实现缺口”，保留证据类型。
- 官方支持与某账号实测是独立信号。401/403、限流、超时、失效模型、协议不支持、资料缺失分别统计。一次失败不能证明服务永久不支持，HTTP 200也必须验证响应内容和终态。
- 同协议原生指客户端请求协议与上游部署提供的协议一致。否则选择已经实现且能表达请求能力的转换；同供应商同时支持多个接口时保留同一部署、模型和账号。依据请求能力判定思考模式，避免为使测试通过而静默关闭用户请求的思考。
- 原生选择在调用前确定；认证失败、限流、流输出或工具副作用出现后，沿用现有重试及回放约束。显式接口缺失可选转换，不能用盲目请求多个猜测URL探测支持情况。
- 跨域官方端点对必须有服务方认证适用范围证据，并通过现有绑定与访问检查。用户自定义端点按显式配置处理。`${AWS_REGION}`、项目ID等模板由实际已授权配置解析；未知模板保留具体缺失原因。
- 文本ACP的适用性结合modalities、工具需求、传输方式、API形态和模型状态判断；实时WebSocket、专用生成和嵌入模型不能仅因含text模态就归为标准Chat接口。Bedrock、Vertex、Azure、Cohere等专有认证/协议需逐项核查既有适配，必要实现与来源计划建立映射，禁止把未知SDK标签默认改成OpenAI兼容后宣称成功。
- 实时检查覆盖已配置且启用的适用模型；其余条目完成官方查询。缺少服务凭据可完成查询任务，不能标为实测通过。最终报告逐条列出实现缺口，适用文本模型的实现缺口修复后才可关闭对应实现任务。
- 15项独立模块验证与先前ACP临时代理实测是历史证据。最终任务使用新构建网关和公开入口，独立验证同一模型的原生与转换链路，确认界面/CLI请求、工作区和模型绑定一致。

## 工程合同

- 所有新文件与测试前缀均为本计划拟定交付，执行者先核实现有同职责文件再落地，调整路径须在对应任务中记录并保持后续任务可发现。
- 元数据扩展仅服务已确认的协议选择需求。先用最小强类型合同表达协议、端点、认证形态、模型适用范围及证据引用，再实现生产装载和消费者。保持一个事实来源，复用已有认证与诊断边界。
- API原始目录保持来源语义；协议补充事实拟存`crates/vw-provider-resolver/assets/model/protocols.json`，查询证据存`docs/dev/model-protocols/`。合并时保留显式配置优先级和远端刷新后补充事实。
- Python审计入口拟为`scripts/audit_model_protocols.py`。任务1定义`inventory --api PATH --shiju PATH --output DIR`及`check-research --inventory PATH --report PATH --group N`；任务20增加`check-coverage --inventory PATH --matrix PATH`，完成前按真实CLI校验后续命令。
- 业务代码、测试和公共结果均不得包含真实密钥或原始敏感载荷。原始响应仅写本机私有临时目录，公开结果留脱敏摘要。真实ACP写入专用临时目录并校验范围。
- 代码任务按批次串行运行全仓格式化与Clippy，审查格式差异范围。纯查询任务不调用Cargo。
