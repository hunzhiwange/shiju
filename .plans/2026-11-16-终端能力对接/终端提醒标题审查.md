## 可实现需求与接线建议（尚未实现）

1. 在现有会话设置里提供独立的“终端提醒”关闭/BEL/OSC9选项及“窗口标题”关闭/状态标题选项，初始均关闭。设置仅属于本地终端宿主，不发送至 Gateway。是否持久化、配置存放位置、中文标签及 OSC9 不支持时的用户提示需产品决定；在决定前不新增配置键。Auto 若以后提供，必须由用户显式选择，禁止把通知失败转为未授权声音。
2. `application.rs` 在 bridge 接受事件后对比业务状态变化，产出纯提醒意图；`runner_stream.rs` 仍负责请求归属与陈旧事件过滤，通知不另建业务状态源。完成只取成功终态，错误只取失败终态，用户取消不报错误；审批/问题等待只在新等待对象到达时触发，不改变审批决策。
3. 去重键建议为会话ID、请求ID、事件类别；审批另加审批/问题ID。相同键在重放、重连、重复终态时只消费一次；新请求可再次提醒。每个请求终态只接受一次，完成与错误互斥，审批解决即撤销待发提醒。缺少稳定归属标识时不以正文哈希猜测，跳过外部派发并保留界面状态。仅保留当前请求和未解决审批的有界记录，会话切换清理，历史恢复不外发。
4. 前台只保留现有界面反馈；后台仅在明确 FocusLost 后允许外部派发；初始/不支持焦点/编辑器返回均视为未知并抑制。FocusGained 清除待发，不补播前台发生的旧事件。若一轮事件批次有多个意图，审批/问题等待优先于错误，错误优先于完成；同批被覆盖项消费后不延迟重播。以后若需跨批限流，先明确产品节流时长，不在本次臆造数值。
5. `terminal.rs` 在 pager 与普通输入分流之前统一处理焦点，并在每轮背景 drain 后、终端仍由应用持有时集中写入；外部编辑器及原生选择暂停期间禁止写 stdout，返回时重新确认状态，不把编辑器焦点当应用后台。焦点不属于 composer 输入，不能流入草稿。
6. 模型仅保存意图、去重与策略所需纯状态；I/O 和后端选择归 `cli-interaction`，终端模式获取及恢复归 `tui-terminal-lifecycle`。不能让 `NotificationStore.message` 任意文本自动变成 OSC 正文，也不能迁入恢复目录的 Codex 配置依赖。

## 字节、安全与隐私边界

以下使用 Rust 风格转义表示字节，绝不将这些示例直接输出到终端：

| 操作 | 当前参考/未来预期编码 | 安全要求 |
| --- | --- | --- |
| BEL | `\x07`，忽略 message | 不保证出声或系统弹窗，取决于终端设置；无正文注入但仍是需显式启用的副作用 |
| OSC9 直连 | `\x1b]9;ShiJu: task complete\x07` | 未来仅传固定模板，另有 task failed / approval required，不传用户消息、回复、命令、文件名、目录、服务名、令牌或错误原文 |
| OSC9 经 tmux | `\x1bPtmux;\x1b\x1b]9;ShiJu: task complete\x07\x1b\\` | 外壳内 ESC 必须加倍；由后端独占添加外壳及终止符；多层 tmux/SSH 不假设自动可用 |
| 窗口标题 | `\x1b]0;ShiJu - working\x07`；清空为 `\x1b]0;\x07` | 固定品牌加 idle/working/needs approval/error 状态，不取会话名称、项目路径或模型原文；净化后再去重，相同标题不重复写 |
| 焦点报告 | 启用 `\x1b[?1004h`，禁用 `\x1b[?1004l`；终端回报 gained `\x1b[I` / lost `\x1b[O` | 生命周期所有者负责开关，不能因设置关闭而遗留报告模式 |

当前 `osc9.rs::PostNotification::write_ansi` 直连分支原样插入 message；tmux 分支 `escape_tmux_dcs_passthrough_payload` 只加倍 ESC。这不是内容净化：BEL 可以提前结束 OSC，ESC/ST 或 C1 OSC/ST 可注入新控制序列，tmux 解封装后同样不安全。不得复用该接口处理任意正文。未来编码边界即使只接固定模板，也应拒绝或剔除所有 C0/DEL/C1，折叠换行与空白、剔除双向/不可见控制并限长，再封装；净化不能承担秘密脱敏，隐私必须由固定模板保证。

标题参考移除 `char::is_control()`、精选 bidi/不可见字符，折叠空白并限制240个 Rust char（不是字节或字素簇）；空内容返回 NoVisibleContent，stdout 非 TTY 返回 Applied 但实际不写。该返回值不能作为已发出证据。标题清理不会识别密钥，仍需固定模板。上游 Screen ASCII 防护应纳入后续适配；未做该适配与平台验证前在 Screen 跳点禁用标题和 OSC9。tmux 标题转发、窗口自动重命名与 allow-passthrough 的实际结果待测，不自动改用户 tmux 配置，不在任意失败后回退 BEL。

## 启停与恢复责任（尚未实现）

- 未启用时不探测/写入标题，不开启为提醒专用的焦点报告，不输出 BEL/OSC9；stdout 非 TTY 时全部跳过。
- 若启用需要焦点报告，由 `tui-terminal-lifecycle` 在进入终端时获取所有权，在初始化部分失败、正常退出、错误返回及 panic 展开时尽力关闭；外部编辑器、原生选择暂停/恢复需与现有 guard 对称，恢复后焦点设未知。强杀无法保证清理，应明确支持边界。
- 标题只在获准并成功写入后登记“本应用已管理”；禁用、退出、错误及释放给编辑器前清空自己管理的标题，不清空从未写过的标题；恢复应用后按当前状态重写。正常路径报告恢复失败，Drop 尽力恢复，不无限重试。
- `clear_terminal_title` 是清空而非还原启动前标题，当前没有跨终端可移植读取方案。不主动查询标题（避免响应进入输入及泄露），也不承诺恢复原值。产品需先接受此限制；要求精确恢复时保持禁用，后续另评估终端特定标题栈能力。
- 外部通知无法撤回，禁用只停止后续输出；去重记录在 I/O 尝试后消费，失败只给本地固定文案反馈，不重试轰炸，不记录正文或密钥。
