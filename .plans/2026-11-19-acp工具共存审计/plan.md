# ACP 工具共存审计计划

目标：逐个核对内置 ACP 补丁的真实作用，查清哪些限制官方工具仅为满足旧验收，并给出保留原生工具的改造建议。

范围：覆盖注册表中的 41 个内置 key，逐个追踪固定上游版本、原版和受管路径、适配器补丁、工具权限、启动校验和现有验收证据。别名随注册 key 核对。

范围外：本计划是只读实现审计及证据汇总。运行时代码与补丁的实施整改另立计划。

假设：现有验收记录和仓库产物足够完成静态分类。缺少匹配版本的证据时记录未知及最小复验路径。

## 设计决策

以挂载工具成功执行并回传为主验收。允许官方工具按原有权限共存。用户显式配置的工具限制和安全门禁仍须生效。

## 架构说明

沿注册表、受管安装与摘要、会话模型启动校验、会话 MCP 转发、代理工具目录及执行链追踪。历史验收与当前入口分别取证。

## 每个适配器的证据

1. 记录适配器 key、上游版本、原版入口、受管入口、平台、相关提交及补丁文件。标明补丁已接入、原型、仅上游能力或无本地补丁。比对注册表、`managed_runtime.rs`、`managed_runtime/contracts.json` 与 `managed_runtime/install.py`。
2. 逐段定位原版是否接收会话级 MCP 声明、发现和向模型公布工具、成功执行、将同一调用的结果交回模型并继续作答。记首个断点及证据。仅有 `initialize` 能力位、模型自行输出或伪造工具结果都不足以证明调用成功。
3. 对每个相关补丁或宿主限制注明改动内容、触发条件、审批及失败行为。单独判断原生能力缺口、只为旧验收排除官方工具、显式名单、安全或权限、模型源及其他作用，可多选。明确普通会话与带 MCP 会话的内置工具是否仍在模型目录、是否可实际执行，区分白名单、仅拒绝名单、无名单及宿主全量拒绝。有补丁也要追到实际入口，不能从名称推断线上行为。
4. 核查原版指定模型能力与 ShiJu `session_model` 受审校验，标出无 MCP 或无名单时是否也被补丁校验挡住。分别陈述 macOS、Linux、Windows 的源码分支或实测依据，记录未实测范围。
5. 比对 [旧计划的验收合同](../2026-11-19-acp动态挂载mcp/plan.md#统一验收合同) 与新的共存标准。写清保留原版、缩小限制、保留协议修复、保留安全逻辑或需先验证的结论及依据。补丁同时处理多项职责时，逐项提出建议，避免整包删除。

## 共存复验口径

- 同一固定版本、项目、副本和权限配置下比较原版与受管版。使用无挂载、挂载、撤除三个新会话。有挂载时，目标 MCP 工具须真正执行成功且由代理把结果交给模型。同名冲突时核对实际服务与调用 ID。无挂载和撤除时核对目标 MCP 工具消失。
- 在原权限允许时探测一个无副作用的官方工具，并验证它与 MCP 工具可在同一挂载会话声明和执行。额外官方工具调用不计为失败。一次模型没选择调用官方工具不足以证明禁用了官方工具。回环模型可有意触发两类调用，记录为协议证据，真实模型证据另记。
- 显式工具名单和宿主禁止规则仍按其语义生效。用独立场景验证批准、拒绝及未遇到 MCP 的普通会话。验收提示与验证逻辑均以真实工具事件和输出为准。历史 `MCP_NOT_AVAILABLE` 精确格式和复杂 RueJS 答案只作为旧验收诊断。
