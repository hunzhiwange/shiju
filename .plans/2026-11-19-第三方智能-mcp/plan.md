# 第三方智能 MCP 改版计划

类型为 ShiJu Iced 原生桌面管理页。

目标是把第三方应用的 MCP 管理集中到「第三方智能 → MCP」，以 CC Switch 的矩阵和编辑流程提升多应用操作效率。

范围覆盖七张截图中的矩阵与搜索、连通性检查、应用导入与结果、重写与 JSON 复制、添加和编辑、模板、JSON/TOML 粘贴、三种传输、目标应用与说明链接。应用列表指此页的应用列和表单内的目标列表。独立应用目录已有「第三方应用列表」计划。

假设页面以当前网关、项目和执行主机为上下文，无需侧栏预选应用。支持与可写性以 ShiJu 的能力、可信安装观察和授权结果为准。保留原生技能页及 ShiJu 自身的 MCP、运行时与 ACP 路径。

## 设计决策

- 延用单应用页改动较小，但仍需逐应用操作。独立矩阵可复用既有目录和网关写入。采用独立矩阵，以本地 CC Switch 提交 `ca58c031` 的 `src/components/mcp/` 和七张截图为交互基线，使用 ShiJu 原生视觉体系。

## 架构说明

- 桌面负责导航和原生交互，受管目录依旧经网关管理。下发、导入和重写交由执行主机，连接、凭据和安装权限继续由各现有服务校验。
- 当前目录公开 DTO 隐去连接定义，原生预览也不含路径。搜索、编辑和导出按服务端安全投影及现有授权设计，详情见任务 2、4、5。

## 开发策略

- 行为改动先写独立的聚焦失败用例。采用真实 reducer、受控网关、临时目录与合成数据，覆盖同名冲突、失败重试、复用修订和旧请求。
- 设计技能用于统一边线、信息密度、真实图标、控件层级、键盘焦点和操作反馈。沿用 ShiJu 明暗主题与 Iced 控件，以原生窗口采证。网页脚手架、动效场景和浏览器检查器不适用于此工作页。

## 公共执行约定

- 开始前读本计划、仓库 AGENTS.md 和自己的编号文件，使用 `/Users/xiangmin/.codex/skills/do-task-plans/SKILL.md`。本计划及入口生成后只读。编号任务负责自身实现、公共接线、验证、提交和清理。调度会话负责派发、等待、状态判定和恢复。
- 在当前分支和工作目录执行，保留既有差异。共享文件由任务声明写入顺序，暂存和提交串行。若同日第三方计划在改 `third_party_settings.rs`，协调共享段落写入顺序并保留彼此路由。这些计划并非功能前置条件。
- 常规可逆事项自主决策并记录依据。遇阻定位根因，采用已有授权内的修复或替代路径，并继续独立工作。关键歧义或新增授权才集中确认。任何实机配置写入、启动 MCP 子进程或外部请求按原入口授权。
- 作用域与请求绑定网关、租户、项目、执行主机、凭据代次、页面代次以及相关记录修订。切页后允许原操作按原身份结算。过期消息不得污染当前界面或改写其他目标。
- 共同遵循原生输入、按钮、弹层、toast 和字体约定。参考 `system_settings_common/` 与 `system_settings_providers/custom_model_modal.rs`。长表单只滚动正文，滚动条 4px、两侧各 7px。遮罩与菜单阻断背景操作。中文和未知字符采用正常字体。品牌图标复用现有资源。
- 任务 1 与 2 各自处理宿主导航与后端，文件不交叉。任务 3–6 分别写矩阵、表单、导入、操作面板模块。它们向任务 7 交付各自的受类型约束入口，任务 7 独占最终桌面组合与跨页测试。

## 公共验证与资源规则

- 本轮仅做计划静态检查。之后仅在用户明确授权测试及桌面编译的范围内执行编号命令与原生验收。无授权时记录未运行项，不用构造 Element、零测试或旧结果冒充行为验证。
- Rust 从仓库根通过 `python3 scripts/cargo_slot.py cargo ...` 执行，重型编译串行且单次 `-j 1`。现有脚本从 1–20 动态领取独占槽位，核验所有权，嵌套复用匹配的存活祖先进程槽位。两个 Cargo 缓存变量使用同一绝对槽位路径。
- 由前台运行句柄追踪本任务进程组，取消或超时后先确认自有 Cargo、rustc、链接器及产物使用者已退出，再重试。仅由原所有者释放槽位，保留缓存和他人锁。记录命令、槽位、缓存路径、退出码、有效测试数与失败数。
- 测试限定受影响包、目标和过滤条件。已通过定向测试编译的同目标无需重复 check。统一回归补跨任务组合与原生渲染，禁止默认全量测试、全仓 lint 或格式化。编译排队不构成实施依赖。

## 公共收尾规则

- 编号文件使用「未开始」「已完成」「待回归」「已阻塞」。状态、失败原因和回归命令只写编号文件。取得当前所需证据后标为已完成并清理编号文件。外部原因导致验收未完成时保留为待回归，核心工作确实受阻时保留为已阻塞。
- 三种收尾状态有本任务实际变更时都先使用 `git-commit` 仅提交本任务改动，如实记录验证和失败，再结束或清理任务文件。只有编号文件自身状态变动或删除时无需空提交。提交失败时保留编号文件和证据。
