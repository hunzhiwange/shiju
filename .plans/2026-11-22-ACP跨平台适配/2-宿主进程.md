# 任务 2 适配 ACP 启动、终端与取消

先阅读并遵守 [公共执行规则](plan.md)，再执行本任务。

批次：【批次 1】 依赖：无

状态：未开始

来源任务：无

目的：用现有 ACP 宿主保证 Linux 上能按原始参数启动、取消并收尾。

## 文件与范围

修改 `crates/libs/acp-host-io/src/spawn_command_options.rs`、`terminal.rs`、同目录独立测试，以及 `crates/libs/acp-client/src/client/process.rs` 和 `process_signals.rs` 的共用启动路径。任务 48 负责后续按适配器接线。

## 上下文

Linux 启动沿用现有命令解析与自有进程组语义。

## 实施

1. 对照安装、ACP 会话与终端入口，保留 argv、cwd 和环境边界。覆盖原生可执行文件、受信 npm shim、带空格/中文路径、无 Node 或命令不存在。优先直接启动受审 JS 入口。
2. 查取消或掉线后子进程、stdio 和资源清理。沿用自有进程组语义，传递独立参数，确保无关进程不受影响。
3. 为 Linux 补参数传递和进程组清理的回归测试源码。ACP 子进程集成边界由任务 49 汇总。

## 验证

- 先写独立回归测试，使用 `acp_platform_spawn` 作为测试名或前缀。旧行为预期失败点为原始 argv 或工作目录不能完整到达子进程，或取消后仍有自有进程。
- 后续在 Linux Docker 容器内使用同一红绿命令 `python3 scripts/cargo_slot.py cargo test -j 1 -p acp-host-io --lib acp_platform_spawn`。仅列为后续命令，本轮不执行。绿灯要求命中本任务测试且零失败。
- 本轮静态逐项检查测试断言、调用者接线及本任务差异。记录受影响目标和待运行项。

ACP 子进程与取消专属红绿测试另用 `python3 scripts/cargo_slot.py cargo test -j 1 -p acp-client --lib acp_platform_process_cleanup`。编写独立测试，旧路径预期在取消后残留自有子进程，绿灯须命中用例且零失败。
