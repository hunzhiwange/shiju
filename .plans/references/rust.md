# Rust 任务的编译内存与定向验证

仅用于 Rust/Cargo 任务。先检查 Cargo.toml、Cargo 配置、测试目标和缓存规则；构建、基础检查及单元测试直接使用原生 Cargo 命令。

## 会话滚动并发覆盖

本节仅在计划含 Rust/Cargo 任务时加载，覆盖主技能默认的 5 会话滚动并发规则；实现与回归阶段均适用。

- 纯 Rust 批次最多 3 个活动任务会话；涉及 Rust 的混合语言任务也计入 Rust 配额。
- 混合批次总活动会话最多 5 个，其中 Rust 最多 3 个；其它语言沿用主技能默认窗口。Rust 配额满时，可补入后续满足依赖的其它语言任务。
- 任一会话完成、进入待回归或暂不可运行时，立即补入依赖和配额均满足的任务，不等待整波结束；始终满足 `总活动会话数 <= 5` 和 `Rust 活动会话数 <= 3`。
- 会话并发与编译资源分开管理；Rust 高内存编译仍串行排队，10 个共享缓存槽位不放宽上述限制。

## 编译内存优先

- 同一仓库的大型 Rust 测试目标或其它高内存 Cargo 编译串行排队，不让多个任务同时重编同一大型 crate。会话可以并行阅读和编辑代码，编译资源单独调度；必要单元测试仍在各任务内完成。
- 内存紧张时，普通 Cargo build/check/test/clippy 使用 `-j 1` 限制单次调用的并发，例如 `cargo test -j 1 -p <包> --lib <过滤条件>`。`-j 1` 不限制其它 Cargo 进程，也不保证降低单个 rustc 的内存峰值，不能替代跨任务编译排队。命令直接调用 Cargo，不经过额外包装入口。
- 复用下述 10 个共享缓存槽位及增量缓存；遵守槽位占用和 Cargo 缓存锁，不创建任务专属缓存，不通过切换 target-dir 绕开编译排队。
- 不为提速清缓存或随意改 profile、features、工具链、增量编译及 codegen 参数；这些改动可能导致重编或增加单个 rustc 峰值。只清理自有进程和锁，保留缓存。
- 编译因内存压力变慢时先减少重叠编译，不反复超时重启或同时启动替代检查。需要判断单个 rustc 异常增长时记录目标、命令及内存变化，另行诊断，不能直接断言泄漏。

## 10 个共享缓存槽位

将以下完整槽位约定写入 Rust 编号任务，保留动态领取、继承复用、双缓存路径、所有权核验及退出清理能力；共享池最多 10 个槽位。

1. 同一仓库所有计划和任务共用 `target/rust-slot-1` 至 `target/rust-slot-10`；槽位编号仅为 1–10，不新增第 11 个槽位、不按任务编号固定分配、不创建任务专属缓存。
2. 从仓库根目录以原子 `mkdir target/rust-slot-locks/slot-N.lock` 领取空闲槽位；仅创建成功者持有。占用时尝试下一个，全部占用时等待，不删除其它活跃任务的锁。
3. 锁中记录真实持有进程 PID 以及任务/会话标识；持有进程须覆盖整个构建、验证及产物使用阶段，不能记录即将退出的临时 shell PID。遗留锁仅在核实持有进程及使用者都已退出后清理；归属或存活状态不明则保持占用。
4. `CARGO_TARGET_DIR` 与 `CARGO_BUILD_BUILD_DIR` 都设置为同一槽位的绝对路径；原生 Cargo 和所有子进程继承，不通过配置、别名或 `--target-dir` 覆盖。二进制等产物也从该槽位定位。
5. 同阶段顺序命令和嵌套调用复用已持有槽位；继承前核验锁的持有 PID 属于当前进程或仍存活的祖先进程，路径与锁对应，不重复领取，不借用其它任务的槽位。无需包装脚本或额外测试运行器。
6. 正常、失败与取消时先结束自有 Cargo、rustc、链接器及仍使用槽位产物的子进程，确认退出后才删除自有占用记录、释放自有槽位锁；保留缓存。不删除其它任务的锁、进程或缓存。
7. 记录实际槽位、两个绝对缓存路径、确切验证命令、退出码和有效测试数；编译成功或零测试不能替代行为验收。
8. 10 是缓存容量，不是编译并发数。会话并发按上文覆盖规则执行，槽位隔离不解除源码、依赖及共享资源约束；同仓库高内存编译仍串行排队，不利用空闲槽位绕过内存限制。

## 取消与进程收尾

- 调用 Cargo 前记录本任务的运行句柄、入口进程及其进程组；直接在前台运行 Cargo，禁止脱离前台进程组启动后台编译。命令超时、工具返回后台句柄或聊天结束不代表 rustc 已退出。
- 取消、超时或退出任务时，先通过原运行句柄停止自有 Cargo 构建，等待其清理 Cargo、rustc、链接器等子进程；仍存活时核对归属，对自有进程组先请求终止，经有界等待仍未退出再强制终止，并再次确认状态。不得按进程名批量杀死其它任务的 rustc。
- 清理完成前不重试同一编译、不启动替代检查，不手工移除 Cargo 缓存锁。若无法确认归属或退出状态，报告具体 PID、父进程、状态及未完成清理，不宣称已停止。正常完成后也确认自有构建子进程已收尾，保留缓存。
- 顺序检查必须在前一步成功后才启动下一步，例如使用 `&&` 或显式判断退出码；不得用无条件 `;` 在测试失败或取消后继续启动 Clippy 等重型编译。清理逻辑仍须覆盖失败和中断。
- 长时间运行时检查父子关系、CPU 时间变化、内存压力和编译输出，区分仍在工作、资源等待与残留进程；不能只因耗时长就反复重启，也不能将“已发终止信号”记为“进程已退出”。

## 任务内必要验证

- 必要单元测试在本任务内完成，指定受影响包、测试目标和有效过滤条件，覆盖本次修改及直接受影响行为；优先复用现有测试，不堆砌无行为价值的测试，也不把必要测试统一积压到最终回归。
- 基础检查按受影响目标选择 `cargo check -j 1 -p <包> --lib` 或对应 `--bin <名称>`；同一目标已被定向测试成功编译时不重复 check，也不再额外 build 一次。
- Rust 按 crate/目标编译，不能只检查修改的 `.rs` 文件；测试名过滤只限制运行范围，仍可能编译整个 lib-test 目标。不能把“小测试”当作“小编译”并行调度。
- 通过原生 Cargo 定向测试获取本次修改后的结果，确认有效测试数和失败数；依靠 Cargo 自身增量缓存复用产物，不额外启动常驻测试运行器，不重复已有效验证的同一目标。
- 记录具体命令、退出码、有效测试数和结果。必要定向测试通过后按任务规则完成；编译成功、零测试或旧结果不能冒充行为验收。客观外部阻塞时记录具体未验收项，不因还有公共整仓检查而把所有任务标待回归。

## 全量检查与统一回归

禁止把无过滤全量测试、workspace 构建、全目标全特性 Clippy 或全仓格式检查写成每任务固定步骤。统一回归补跨任务集成和必要公共检查，公共命令合并一次；已通过且未受后续改动影响的单元测试不机械重跑。只有用户明确要求或项目明确的统一回归流程要求时才运行全量测试。格式化限定本次修改文件，不连带修改他人文件。
