# ACP 双档权限验收

范围为生产 `/v1/global/config/acp/defaults` 返回的 22 个后端。权限矩阵另外核对兼容别名、旧命令和同名命令覆盖。以下观察来自 Darwin arm64 的固定版本验收。表中的版本是复现用版本，只有实测行才能据此判断权限行为。

宿主接到 `fs/write_text_file` 时，可以核对当前会话、工作区和文件边界，再直接执行连续编辑。未明确授予完全访问时，单独传入 `ApproveAll` 会回落为普通审批，终端和工具回调也遵守这一规则。完全访问回调只选择单次许可。进程内工具、供应商自带的审批系统与宿主 ACP 回调各自有独立执行边界。

“两档”在模型来源列指客户端模型与智能体原生模型，客户端模型仍以生产能力接口和已安装的审核版本为准。未运行行的版本与离线配置状态取自[固定版本清单](cli-versions.json)。

固定版 Codex 的 `agent` 使用自动审查，`workspace-write` 和 `agent` 都保留系统临时目录写入。桌面审批档改为请求并确认 `read-only`，恢复与显式设置也遵守这一限制。现有非桌面模式保留逻辑继续按原有配置工作。

真实 Claude 在隔离网关中收到两次工作区写入、一次越界写入、一次命令和一次删除。完全访问阶段产生相应文件变化，两个审批阶段均无写入副作用。原生模型路径回读为 `default → bypassPermissions → default`。客户端模型路径运行结束后未取得网关存活会话回读。真实 ACP 回退用例另外检查原生审批请求及组织拒绝规则。

## 复现

先按编号任务的共享槽位规则设置 `CARGO_TARGET_DIR` 和 `CARGO_BUILD_BUILD_DIR`。真实 Claude 验收需要将已安装的固定版 `claude-agent-acp` 加入 `PATH`。脚本只启动受控的回环网关和固定版适配器，使用临时项目和模型端点。

```sh
cargo test -p vw-acp --lib acp_desktop_approval_backend_matrix -- --test-threads=1
cargo test -p vw-acp --lib acp_full_access_ -- --test-threads=1
cargo build -p vw-cli --bin shiju
python3 scripts/verify_acp_approval.py --gateway "$CARGO_TARGET_DIR/debug/shiju" --output target/acp-approval-evidence/matrix.json
```

JSON 将宿主协议夹具与真实适配器行分别记录。未知自定义 key 在宿主协议测试中覆盖，桌面网关拒绝把该 key 绑定到智能体配置。Codex 同名替换程序通过网关三阶段测试，其结果仅说明宿主 ACP 回调的行为。存在失败或缺证据的真实适配器时，脚本以非零状态退出。
