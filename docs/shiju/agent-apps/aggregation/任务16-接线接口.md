# 任务16共同发布接线接口

本接口在原检出实施。任务16的35项聚焦检查与最终全仓Clippy通过，完整边界及证据见 `任务16-验证.md`。

- 原 `ProviderTransactions` 的 `Pending` 追加 `provider_record: Option<ProviderRecordChange>`，共同记录意图使用 **version 10**；version 8 保留 Codex 设置，version 9 保留 OMO。原恢复器遇到共同记录意图明确拒绝并保留，禁止丢弃记录参与者。
- `providers/live/record_publication.rs::ProviderRecordChange` 强类型绑定操作ID、执行主机、项目、应用、供应商ID及记录前/后像，`dependencies` 冻结其他成员的原记录。只写原私有事务根，不记录载荷。`ProviderRecordParticipant` 的 `reserve/finish` 由原 `AppProviderStore` 实现，不新建聚合存储。
- `commit_project_record` 同原物理guard和主机状态锁保存 durable intent，逐行CAS预留本次完整目录输入（发生中途冲突时由同一未发布意图撤销已领取的预留），再标记发布、写文件、CAS落定记录、落定原状态、清除意图。`recover_project_record` 要求授权项目、原guard及数据库参与者；发布前撤销本意图的预留，发布后前滚。不同项目/租户/预留拒绝；外部编辑使共同意图无法完整恢复时保留意图与预留，不宣称完成。
- 原供应商记录命名空间内临时保存预留封装。`ProviderRecordStore` 读取仍返回已提交前像，普通CAS及删除不能匹配预留封装；原有账户/供应商编辑不覆盖在途记录。恢复后清除封装；仍在名单中的记录保留原主机/项目绑定，普通无作用域CAS明确拒绝，移除成员在同一意图解除本绑定。没有建立第二份生效目录。
- `gateway/api/handlers/aggregation_resync::configure` 在既有供应商写授权后核对聚合项目写授权、预像与聚合修订；生效时另验原项目路由权限和唯一 `RoutingControl`。输入 `AggregationWriteQuery {project_id, expected_revision}`，修订来自任务39。不存在名单时保留原目录保存行为；已有名单却缺少项目/修订则拒绝。Bearer与旧管理头只准同一主体，不允许借两个令牌拼接权限。
- `AppProviderStore::resync_context()` 取得上述已授权上下文；成员/默认项所有者在内存构造 candidate `AppState` 后调用 `RecordPublicationContext::publish_candidate(&candidate)`。不得先调用 `set_member` 落定候选再重发布。相同候选是空操作；生效时文件、stack/default及记录参与原事务；停用时只落定计划状态。上下文携带原修订，提交前重新读取来源和原生文件重验。
- Claude/Codex供应商表单与配置保存使用原 `AppProviderStore` 写法，配置上下文后其原CAS接入同一发布器。Claude复用 `claude_publish::plan`；Codex复用 `codex_publish::plan`。两者沿用原规则，不复制目录算法。
- 通用聚合校验、Claude路径及原监听共同发布接口由任务16维护；Desktop专属数据面由任务46维护。`RoutingControl::publish_aggregation_app` 是按应用授权的提交包装；原Codex包装保留。不要覆盖 `route_auth.rs` / `dispatch.rs` 中其他任务在途修改。

当前限制必须显式拒绝：官方/受管账号未由实际账号所有者提供恢复证明；未接管的外部Codex目录；不支持的上游协议。Claude认证形式是显式目标标记，不根据令牌字符串猜测；原生Codex Responses使用原监听的同协议转发，Chat转换分支继续保持原边界。任何失败均不得先把新provider修订写成已生效。具体测试、范围及最终证据在任务16验收文档完成后记录。
