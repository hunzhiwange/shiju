## 实现与边界

- 原 `POST /v1/app-providers/pi/config/state` 增加项目视图，返回 `PiDirectoryState`；`PUT /v1/app-providers/pi/{id}/directory-entry` 接收 `PiDirectoryWrite` 与严格判别的 insert/replace/remove。DTO 在 `vw-api-types/src/agent_apps/aggregation.rs`。remove 使用空结构体变体，避免 Serde 无载荷变体忽略未知字段。
- 原 Pi router 挂载新写路由并分派 scoped/legacy 状态读取。只读不创建事务或目录、不认领项目、不恢复 pending；旧入口访问已绑定项目的原生槽位返回冲突。未绑定旧状态必须先由可信执行端证明归属并绑定，本 API 不推断项目。
- 复用原策略中 provider_config_read/write 与同项目、应用的 aggregation_read/write。同一 Bearer、租户、主机、项目和应用均校验。Host.pi_directory 为受信主机设置，优先于执行主机 PI_CODING_AGENT_DIR 和默认目录；请求不接受路径。
- `PiFiles::apply_directory_change_for_project` 在原生 Pi 所有者补齐项目事务接线，复用表单声明校验、JSON 补丁与 commit_project_checked，不认领旧槽位。固定只写 models.json，保留其他供应商、扩展字段和嵌入凭据；auth.json 与 settings.json 不写入。
- 修订使用原 HMAC 签名，绑定主体、主机、ProjectScope、事务状态、原生模型源修订与默认项。写入在物理目录锁内复核，响应修订生成前持续持锁；读取前后复核输入。无权限、陈旧修订、缺失替换、重复插入、pending、不安全配置和执行失败均明确返回错误；响应不回显原生配置或凭据，scoped 读取与错误为 no-store。
