# 项目组合写操作边界

## 任务 17：组合写入串行边界

`ProjectProfileStore::with_operation(tenant, work)` 是组合存储唯一业务入口；构造器之外的读取与写入移至仅在该同步闭包内可取得的 `ProfileOperation`。调用方必须先完成项目、目标主机和各领域授权，再在阻塞执行线程内把 prepare_switch、四类 apply、最终 select 放在同一个闭包内。create_from_current、resnapshot、rename、delete、save、select、clear 都使用同一上下文。clear 仅清当前授权项目的主机/组指针，不撤销原生配置，其他项目占有该槽位时拒绝；空指针可重复清理。后续入口不能另开无锁路径。租户不一致在快照读取或存储访问前拒绝，主机继续核对可信执行端身份。上下文禁止跨线程传递，嵌套组合操作直接报错。

`profile_operations.rs` 一次领取租户与执行端两个资源；租户键覆盖跨主机共享实体冲突，执行端键保守覆盖跨租户/组的物理应用目录别名，不以项目或请求主机别名分锁。同租户和同执行端的组合操作分别串行，读取快照到落盘期间不会夹入另一个组合 apply。资源表互斥量只用于领取/释放，不跨业务调用持有；RAII 在成功、错误及 unwind 时释放。本边界是进程内执行端协调，不能用于承诺多进程或外部客户端原生文件写入隔离；存储事务与版本前提仍保留。

锁秩为组合外层资源 → 领域 catalog/record → 原生 app/directory → 领域存储事务。直接单项切换仍通过原有领域锁，组合不能预持 AppWriteGuard 再调用同一领域入口，也不能在数据库事务回调中执行原生读取。外层不同时占用四类物理锁、不覆盖部分失败恢复、不整组回滚。单项切换目前没有统一外层门闩，故只能保证各领域自己的提交边界；若后续要求快照相对所有直接单项修改也具备跨领域原子观察，必须由这些入口共同接入外层协调，当前不能宣称已具备该保证。

本轮按最新用户要求只写代码与必需契约，没有编写或运行测试，未执行 Cargo、构建、检查、实机或回归；未领取 Cargo 槽位，CARGO_TARGET_DIR 未设置。任务 3 存储、来源 PROFILE_LOCK 及原生 write_guard/MCP 锁顺序已经阅读；当前没有组合生产 API/apply 调用者，后续接线必须保持完整闭包。实现未经编译和行为验证；恢复验证后需补 profile_t17_ 的暂停 apply 与 rename/delete、快照/clear 互斥、跨主机共享实体、租户拒绝、错误/取消释放与嵌套拒绝场景。
