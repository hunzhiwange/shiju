## 接口与授权

- `GET /v1/app-routing/hosts/{targetHostId}/status` 与 `GET /v1/app-routing/hosts/{targetHostId}/health` 要求主机级 `routing_read`。`POST /v1/app-routing/hosts/{targetHostId}/start` 与同前缀的 `POST /stop` 要求 `routing_manage`，请求体为空 JSON 对象。
- 网关继续用 skey 与租户中间件保护客户端入口。管理接口再校验 `x-agent-apps-token` 对应的管理员策略成员，以及匹配平台、公司和执行主机的显式许可。由 `SHIJU_AGENT_APPS_ACCESS_FILE` 指定现有私有管理员策略，在对应成员的 `grants` 条目加入 `routing_read`、`routing_manage`。两个字段默认关闭，分别授权。单一监听器在网关启动时绑定唯一租户和主机，存在多个控制作用域或与启动恢复主机不一致时拒绝该策略。策略成员和许可按请求重读。
- 手动启动使用同一主机策略的 `routing_startup` 监听地址和端口，`enabled` 只控制网关启动时自动恢复。默认回环地址为 `127.0.0.1:15721`，端口 0 由系统分配。接口复用 `RoutingListener` 的状态机、实际绑定地址与启动时间。停止会拒绝已附接应用，或等待监听与连接任务回收。控制端点使用 `Cache-Control: no-store`。
- 健康响应只包含 `ready`，表示监听器已运行。错误用 `ApiErrorBody`，例如 `not_ready`、`address_in_use`、`transition_in_progress`、`apps_attached`。SDK 的 `GatewayClient::app_routing_status`、`app_routing_health`、`app_routing_start`、`app_routing_stop` 复用现有认证与租户头，保留 HTTP 状态和结构化错误。客户端复用禁止重定向和重试的原生传输。
- 生产数据面、附接发布事务与非回环开放保留各自验收任务。WSL 地址保留在来源映射，Windows、Linux、WSL 范围外且未验证。
