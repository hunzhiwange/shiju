# 任务看板与工作流

任务看板是 Agent Scheduler 的可视化客户端。工作流、状态角色、阶段动作、人员编排和 worktree
resource 都由 gateway 返回 DTO；桌面端只渲染这些 DTO 并提交 command。

## Workflow 读模型

项目 workflow 来自：

```http
GET /v1/agent-scheduler/projects/{project_id}/workflow
```

任务快照也会携带 `read_model.workflow`。看板列使用 `TaskPoolWorkflowSnapshotDto.statuses`：

```json
{
  "id": "dev_lifecycle",
  "label": "Development Lifecycle",
  "statuses": [
    {
      "key": "pool",
      "label": "任务池",
      "role": "backlog",
      "auto_execution_candidate": false,
      "is_scheduling_backlog": true,
      "next": "pending"
    },
    {
      "key": "pending",
      "label": "待执行",
      "role": "queued",
      "auto_execution_candidate": true,
      "occupies_execution_slot": false,
      "next": "running"
    },
    {
      "key": "running",
      "label": "执行中",
      "role": "executing",
      "auto_execution_candidate": true,
      "occupies_execution_slot": true,
      "next": "code_complete"
    }
  ]
}
```

客户端只使用 `key`、`label`、`role`、`terminal`、`next`、`transitions` 渲染列和按钮状态。
是否允许某次转移由 command 响应决定。

## Lifecycle-first 自动调度

自动调度不由看板指定目标状态。看板提交 `start`、`retry`、`run_stage_action` 等用户意图后，gateway 根据当前
`status_key`、lifecycle transition outcome 和 status role 解析下一阶段，再把下一阶段投影为兼容运行态。

看板可以展示 `next`、`transitions` 和可用按钮，但不能把这些字段当成本地状态机执行。后台调度遇到未知 workflow、
停用状态、缺少 transition 或无法映射的 role 时，应显示 gateway 返回的错误或刷新后的快照，不在客户端推断替代目标。

## Status Role

`TaskPoolWorkflowStatusRoleDto` 是跨 workflow 的最小语义层：

| role | 客户端用途 |
| --- | --- |
| `backlog` | 展示待提升任务 |
| `queued` / `planning` | 展示可执行队列 |
| `executing` | 展示运行中和执行 slot 占用 |
| `review_ready` / `review` | 展示审核动作 |
| `merging` | 展示合并动作 |
| `paused` / `failed` | 展示阻塞原因和重试入口 |
| `done` | 展示完成归档入口 |

客户端不能用 role 自行推进状态；role 只决定 UI 分组、按钮可见性和提示文案。

## 任务卡片字段

`AgentSchedulerTaskBoardTaskDto` 是卡片最小契约：

- `task_id`、`status_key`、`status`、`priority`、`order_no`
- `model`、`agent`、`acp_agent`、`prompt`
- `run_id`、`run_stage`、`workspace`
- `last_error`、`pause_reason`
- `merge_source_branch`、`merge_target_branch`
- `selected_worktree_path`、`selected_worktree_slot_id`、`selected_worktree_branch`
- `read_model.title`、`workflow_id`、`status_label`、`status_role`
- `read_model.stage_id`、`stage_label`、`staff`、`stage_action`
- `read_model.available_stage_actions`

卡片标题优先使用 `read_model.title`，状态列优先使用 `status_key` 匹配 workflow。
`status` 是兼容枚举，不能覆盖 `status_key`。

## 阶段动作

阶段动作由 `AgentSchedulerTaskBoardStageActionDto` 表达：

```json
{
  "stage_id": "code_review",
  "capability_id": "saved_workflow",
  "workflow_uuid": "00000000-0000-4000-8000-000000000101"
}
```

客户端点击阶段动作时发送：

```json
{
  "task_id": "task-123",
  "command": "run_stage_action",
  "reason": "运行阶段动作",
  "payload": {
    "stage_action": {
      "stage_id": "code_review",
      "capability_id": "saved_workflow",
      "workflow_uuid": "00000000-0000-4000-8000-000000000101",
      "member_id": "staff-reviewer"
    }
  }
}
```

`available_stage_actions` 用于渲染可选动作；是否能执行仍由 gateway 校验。

阶段动作只表达能力和输入，不表达目标列。执行结果成功、失败或阻塞后，由 gateway 按当前 lifecycle transition
写入新的 `status_key`、`status_role` 和兼容 `status`。

## 人员编排 Staff 投影

人员编排配置由 staff projection 返回：

```http
GET /v1/staff/projects/{project_id}/projection
```

任务卡片中的 `read_model.staff` 只展示当前阶段负责人：

```json
{
  "member_id": "staff-reviewer",
  "member_role": "reviewer",
  "primary_member_id": "staff-reviewer",
  "backup_member_ids": ["staff-reviewer-backup"],
  "manager_member_ids": ["staff-lead"],
  "autonomous": true
}
```

`autonomous` 只表示该阶段允许 Agent Scheduler 在明确 wake 或 command 路径中自动接续，不是桌面端本地调度开关。
旧的任务池自动执行、任务拆分和代码审核开关不再参与调度；客户端只提交阶段能力和自主调度配置。

变更阶段负责人、候补或管理成员时使用 staff command 或 `assign_staff` command。staff command 只表达人员编排意图，执行调度仍由 Agent Scheduler 处理。客户端不要本地重算阶段负责人。

## Review 与 Merge

审核和合并结果必须来自 Agent Scheduler 快照或事件：

- 审核启动：`command=run_stage_action` 或 `command=start/retry`。
- 审核完成：读取 `/tasks` 中新的 `status_key`、`last_error`、`pause_reason`。
- 合并锁：通过 `/v1/task-pool/worktrees/merge-lock` 与 `/merge-unlock` 申请和释放。
- 合并结果：由 gateway 写入任务事件、日志和状态快照。

客户端可以显示日志与产物，但不能从 diff、分支名或命令输出推断最终状态。

代码审核和 Git 合并只有在当前阶段绑定了 `code_review` 或 `git_merge` 能力时才会执行。非开发 workflow
不会因为状态 role 是 `review` 或 `merging` 而隐式继承代码审核或 Git 合并。

## 手工移动边界

拖拽和批量移动仍使用 `command=move`，但它们是临时人工修正通道，不是自动调度流程的一环。客户端只在用户明确拖拽
或执行批量操作时发送 `move`；`run_stage_action`、dispatch wake、policy 处理和 worker event 不能退化为发送
`move` 来完成状态推进。

`move` 被接受后仍以 gateway 快照为准。客户端不得因为本地拖拽成功就把该状态变化作为后续自动调度的依据；下一次
自动动作仍必须从刷新后的 lifecycle `status_key` 和 status role 开始。

## 旧数据迁移

旧桌面任务文件只作为迁移输入。导入后使用 `/v1/agent-scheduler/projects/{project_id}/legacy-import`
写入 gateway，再从 `/tasks` 重建看板。迁移入口不参与 JS 客户端正常读写路径。
旧配置中的 `auto_execute`、`auto_promote_pool_tasks`、`code_review_enabled`、`task_split_enabled`
及对应 `task_board_*` key 会被忽略，不创建阶段能力绑定，也不提示迁移。
