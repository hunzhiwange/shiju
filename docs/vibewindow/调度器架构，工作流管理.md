# 调度器架构与工作流管理

本文说明 Agent Scheduler 任务执行调度中容易混淆的职责边界：生命周期工作流、语义角色、生命周期桥接层、
阶段能力、任务看板手工移动和已保存 Workflow。

## 职责边界

### 生命周期工作流

生命周期工作流定义任务有哪些状态、状态顺序和成功/失败后去哪里。

生命周期定义由 `vw-agent` 通过 `/v1/task-lifecycle/workflows` API 保存、校验和查询。桌面端
Workflow Manager 只是 gateway client 和 UI：启动或刷新时读取生命周期 DTO，保存/删除时调用
gateway，任务看板消费本地 cache 中的状态 key、label、`StatusRole` 与转移边。

示例：

- `dev_lifecycle`：任务池 -> 待执行 -> 执行中 -> 代码审核 -> 合并 -> 完成。
- `marketing_campaign`：活动想法 -> 待策划 -> 投放 -> 复盘 -> 结案。
- `recruiting_pipeline`：人才池 -> 初筛 -> 面试 -> 评审 -> Offer -> 入职。

生命周期工作流回答的是：

```text
任务现在在哪个阶段？
成功后去哪？
失败后去哪？
```

### 语义角色 `StatusRole`

语义角色不是人员角色，也不是可执行 Workflow。它是状态的调度用途标签。

它回答的是：

```text
这个状态在 Agent Scheduler 眼里应该被当成哪类阶段？
```

例如不同生命周期里的状态名不同，但调度语义相同：

| 状态 key | 语义角色 |
| --- | --- |
| `pending` / `campaign_queued` / `recruiting_queued` | `Queued` |
| `running` / `campaign_running` / `recruiting_interviewing` | `Executing` |
| `code_review` / `campaign_reviewing` / `recruiting_reviewing` | `Review` |
| `pr_submitted` / `campaign_closing` / `recruiting_offer` | `Merging` |

语义角色决定“能不能调度”和“默认属于哪类动作”：

| 英文值 | 中文显示 | 调度含义 |
| --- | --- | --- |
| `Backlog` | 待办 | 可通过阶段能力或自主调度推进到下一阶段，不直接执行。 |
| `Queued` | 排队 | 可由 Agent Scheduler 根据阶段负责人、显式命令或 wake 启动执行。 |
| `Planning` | 准备 | 可启动拆分/准备任务，计入执行并发。 |
| `Executing` | 处理中 | 已占用执行并发，参与运行超时监控。 |
| `Failed` | 失败分支 | 可重试，通常回到排队或准备阶段。 |
| `Paused` | 暂停 | 不自动调度，等待人工恢复。 |
| `ReviewReady` | 待审核 | 可进入审核；如果配置阶段能力，则按能力执行。 |
| `Review` | 审核 | 审核类阶段；成功进入下一阶段，失败走 failed 边或暂停。 |
| `Merging` | 收尾 | 收尾/合并类阶段；可运行 `git_merge` 或业务收尾能力。 |
| `Done` | 成功 | 已完成，不再调度，可进入归档。 |
| `Archived` | 归档 | 终态，不再调度。 |
| `Custom` | 其他 | 展示或自定义阶段，系统不施加自动调度语义。 |

界面上应显示中文，例如“待审核”；持久化值仍是英文，例如 `ReviewReady`。

### 生命周期桥接层与运行态投影

Agent Scheduler 的自动状态变化必须先经过 lifecycle bridge。桥接层只做三件事：

- 把当前 `status_key` 解析为 lifecycle 状态，并确认目标状态存在且启用。
- 把 `status_key -> status_role -> AgentTaskStatus` 投影为运行态，例如 `queued` / `planning` 映射为
  `Queued`，`review_ready` / `review` / `merging` 映射为 `Submitted`。
- 把 `from_status_key + outcome` 解析为下一阶段，再把下一阶段投影为运行态。

因此自动推进输入是 `success`、`failure`、`blocked`、`retry` 等 outcome，而不是目标状态 key。遇到
workflow 缺失、状态停用、没有 outcome transition，或 `Custom` 等无法映射的 role，自动路径必须返回明确错误
或跳过并记录原因，不能退回到旧枚举、默认列名或手工移动补偿。

运行态 `AgentTaskStatus` 只表达调度执行状态，不能反向决定 lifecycle 阶段。任务看板读模型中的
`task_board.status_key` / `task_board.status_role` 是 lifecycle 的投影；状态变化必须同时更新投影，避免运行态
和看板列分叉。

### 阶段能力

阶段能力是项目级执行配置，定义某个生命周期阶段在被启动时具体执行哪类动作。配置项位于
`staff.project_state.stage_actions`，使用稳定能力 id：

| 能力 id | 中文显示 | 适用说明 |
| --- | --- | --- |
| `advance_status` | 推进状态 | 用于积压池或失败分支，沿工作流下一阶段推进。 |
| `execute_task` | 执行任务 | 用于排队或规划阶段，进入任务执行路径。 |
| `code_review` | 代码审核 | 内置代码能力，适用于 `ReviewReady` / `Review`。 |
| `git_merge` | Git 合并 | 内置代码能力，适用于 `Merging`。 |
| `saved_workflow` | 已保存 Workflow | 业务自定义入口，必须提供 `workflow_uuid`。 |
| `manual` | 人工处理 | 记录人工接管，不通过人员编排开始命令自动执行。 |

阶段能力回答的是：

```text
任务到这个阶段时，具体执行哪种能力？
```

阶段能力不直接写目标状态。`advance_status`、`code_review`、`git_merge`、`saved_workflow` 等能力只执行动作并
交回 outcome；下一阶段仍由当前 lifecycle transition 决定。`manual` 能力表示人工接管，不能通过人员编排的开始
命令自动执行。

旧的“自动执行任务池”“任务拆分”“代码审核”全局开关已经移除。任务池推进、任务拆分、代码审核和 Git
合并都必须通过能力目录中的能力和当前项目的阶段绑定表达；未绑定能力时，Agent Scheduler 不生成等价动作，
也不从旧配置 key 推断迁移。

示例：

```toml
[[staff.project_state.stage_actions]]
stage_id = "recruiting_offer"
capability_id = "saved_workflow"
workflow_uuid = "00000000-0000-4000-8000-000000000204"
```

含义：

```text
招聘流程进入 Offer 跟进阶段时，运行这个已保存 Workflow。
成功后按 recruiting_pipeline 的 succeed 边推进。
失败后按 failed 边推进；没有 failed 边则暂停。
```

### 已保存 Workflow

已保存 Workflow 是当前开放的业务自定义自动化。它不是任意用户代码插件，也不是新的能力类型；
它通过阶段能力 `saved_workflow` 被引用。

运行 `saved_workflow` 时只传必要上下文，例如 Workflow UUID、任务摘要、阶段 key、成员和优先级。
不传密钥、完整 prompt、日志全文、diff、文件内容或 worktree 路径。运行结果再映射回当前生命周期
workflow 的 `succeed` / `failed` 边。

## 共享数据库边界

项目、配置、gateway、调度、会话、生命周期工作流、已保存 Workflow 和知识库共用一个用户级全局数据库。
用户长期选择 SQLite 或 PostgreSQL 中的一个后端；缺少配置时保持 SQLite 默认行为。

- debug 配置：`~/.vibewindowdev/database/config.json`
- release 配置：`~/.vibewindow/database/config.json`
- SQLite 数据：同目录的 `vibe-window.sqlite3`

`config.json` 只接受以下形式；provider 必须是小写 `sqlite` 或 `postgres`，未知字段会被拒绝：

```json
{"provider":"sqlite"}
```

```json
{"provider":"postgres","schema":"vibewindow"}
```

PostgreSQL 的连接串固定从 `VIBEWINDOW_DATABASE_URL` 读取，不写入 `config.json`。schema 缺省为
`vibewindow`，且必须是最长 63 字节的安全标识符。URL 必须显式包含 `sslmode=require` 或
`sslmode=disable`；`require` 使用 WebPKI 根证书验证服务端证书，`disable` 只适合可信本地环境。
`GlobalDatabase` 按配置文件绝对路径在进程内固定首次成功选择的后端和连接池，后续 Store 与请求只复用该
provider；修改 `config.json` 或 URL 后必须重启进程。

### 31 张逻辑共享表

SQLite 与 PostgreSQL 的 DDL 由同一领域 Store 分别拥有；除全文索引的方言对象外，对应表的主键、租户条件、
外键删除语义和查询稳定排序保持一致：

| 领域 | 数量 | 逻辑表 | provider 所有者 |
| --- | ---: | --- | --- |
| 项目注册 | 3 | `platform`、`company`、`projects` | `ProjectStore` |
| 系统配置 | 1 | `system_configs` | `SystemConfigStore` |
| Gateway 设置 | 1 | `gateway_settings` | `GatewaySettingsStore` |
| Gateway 密钥元数据 | 1 | `gateway_skeys` | `GatewaySkeyStore` |
| Agent Scheduler | 11 | `scheduler_meta`、`scheduler_tasks`、`scheduler_runs`、`scheduler_task_logs`、`scheduler_task_artifacts`、`scheduler_run_workspaces`、`scheduler_events`、`scheduler_outbox_messages`、`scheduler_workers`、`scheduler_teams`、`scheduler_resource_leases` | `AgentSchedulerStore` |
| 会话 | 6 | `session_index`、`session_messages`、`session_calls`、`session_steps`、`session_todos`、`session_agent_sessions` | `SessionStore` |
| 生命周期 | 1 | `workflow_lifecycle_workflows` | Task Lifecycle Store |
| 已保存 Workflow | 1 | `workflow_workflows` | Workflow Store |
| 知识库 | 6 | `knowledge_datasets`、`knowledge_documents`、`knowledge_index_jobs`、`knowledge_chunks`、`knowledge_chunks_fts`、`knowledge_embedding_cache` | Knowledge Store |

调度与会话表通过完整项目作用域外键关联 `projects`；会话子表按同一项目内的 session 级联删除。
知识库的 dataset/document/chunk/job 外键包含租户列。SQLite 的 `knowledge_chunks_fts` 使用 FTS5，
PostgreSQL 使用生成的 `tsvector` 和 GIN 索引，并保留参数化 `ILIKE` 回退；两端都保持租户、过滤、数量和
稳定排序契约，但不承诺全文检索分数数值相同。领取任务、租约、outbox 和知识索引任务在 PostgreSQL 使用
事务与 `FOR UPDATE`/`SKIP LOCKED`，schema 初始化使用事务级 advisory lock。

两类工作流保持独立表语义：

- `workflow_lifecycle_workflows` 保存用户级生命周期定义；定义经 gateway/桌面链路转换为项目调度快照。
- `workflow_workflows` 保存 UUID 及 Workflow YAML；`saved_workflow` 阶段能力按 UUID 读取并补齐 YAML。

两表不互相合并，也不伪造项目外键或项目作用域。旧
`task-lifecycle/workflows.sqlite` 与 `workflow/workflows.sqlite` 不读取、不迁移、不删除，也不会因新写入而创建。

### 隔离、安全与运维

- 每个进程只构造所选 provider；不探测、不连接未选择端，也没有跨端读取、回退、复制、合并、迁移或双写入口。
- 两端数据完全不互通。切换前由用户自行迁移和校验数据，切换后重启；旧端数据原样保留，系统不会读取或删除。
- SQLite 保持 WAL、外键、busy timeout、`0700` 目录、`0600` 文件与 schema 锁。
- PostgreSQL 使用 `$n` 参数、`BIGINT`/`BYTEA`、受控 `search_path` 和经校验引用的动态标识符；用户输入始终绑定参数。
- 错误可包含后端、schema 和操作名，但不得包含 URL、用户名、密码、令牌或原始敏感载荷；Gateway 密钥只保存哈希和掩码。

cron、memory provider、WhatsApp、Agent IPC、外部 iMessage 数据库以及 APIQL/AI-DATA 用户数据源等独立
SQLite/外部数据库不属于这 31 张表，不受全局后端选择影响。

### 本地 PostgreSQL 验证资源

真实 DSN 只从 `VIBEWINDOW_TEST_POSTGRES_URL` 注入。fixture 每次生成随机 `vw_test_<uuid>` schema；创建和
清理前都验证前缀与 32 位十六进制 UUID，只删除自己创建的 schema，不读取、覆盖、迁移或删除本地已有业务
schema。SQLite sentinel 用于确认 PostgreSQL 测试未触碰 SQLite 数据。

| 本地 profile | Rust 映射 |
| --- | --- |
| `MaxIdleConns=10` | 仅保留为未映射基线；`r2d2` 没有最大空闲连接上限，不映射为 `min_idle` |
| `MaxOpenConns=100` | `r2d2.max_size=100` |
| `MaxLifetime=300s` | `r2d2.max_lifetime=300s` |
| `Debug=false` | SQL debug logging 关闭；fixture 拒绝启用 |

仓库门禁编译这些双后端测试源码，但本计划禁止执行 `cargo test`，不得把未运行的运行时测试描述为已通过。

## 开发生命周期为什么有代码审核和合并

`StatusRole` 只说明状态属于哪类调度槽位，不等于具体业务实现。

开发生命周期会显式补齐默认阶段能力：

- `ReviewReady` / `Review` 默认配置 `code_review`：构造审核 prompt、检查 worktree、读取 diff、运行 reviewer。
- `Merging` 默认配置 `git_merge`：检查 source/target branch、merge lock、执行合并。

所以开发生命周期里有很多代码路径，是因为它给审核和合并阶段配置了内置代码能力。

招聘流程里的这些状态虽然也可能使用 `Review` 或 `Merging` 角色，但业务含义不同：

- `recruiting_reviewing` 的 `Review` 是候选人评审，不是代码审核。
- `recruiting_offer` 的 `Merging` 是 Offer 跟进，不是 Git 合并。

因此非开发 workflow 不应该默认落到代码审核或 Git 合并。

## 推荐 Agent Scheduler 调度规则

建议明确区分开发 workflow 和业务 workflow：

```text
dev_lifecycle:
  ReviewReady / Review -> 显式绑定 stage_actions.code_review 后执行代码审核
  Merging -> 显式绑定 stage_actions.git_merge 后执行 Git 合并

marketing_campaign / recruiting_pipeline / 其他业务 workflow:
  Backlog / Failed 未配置阶段能力 -> 沿下一阶段推进
  Queued / Planning 未配置阶段能力 -> 进入默认执行路径
  ReviewReady / Review / Merging 未配置阶段能力 -> 明确提示需要配置阶段能力
  配置 saved_workflow -> 运行绑定的已保存 Workflow
  不回退到 code_review 或 git_merge
```

这样更安全，也更符合用户直觉。

## 任务看板和手工移动

任务看板是 lifecycle 读模型的客户端，不拥有自动调度状态机。看板可以提交 `command=move`，批量移动也可以继续
提交多个 `move` command，但这些入口只作为临时人工修正能力保留：

- 手工移动表达“用户要把这张卡放到某列”，用于纠错、恢复历史数据或人工介入。
- 手工移动可以更新 `task_board.status_key` 和兼容运行态，但事件语义是 `HumanIntervened`，不是自动调度成功。
- 自动路径不得把 `move` 当作 stage action、dispatch、policy 或 worker event 的前置步骤。
- 自动路径不得在 lifecycle transition 缺失时悄悄改用手工移动或批量移动完成状态推进。

## 工作流管理放什么

工作流管理更适合管理 gateway 中的生命周期模板：

- 状态 key。
- 状态显示名。
- 语义角色 `StatusRole`。
- succeed/failed/manual 等结果去向。

保存边界：

- `vw-agent` 校验 workflow id、状态 key 唯一性、`next` 和 transition target 是否存在。
- `vw-agent` 把自定义生命周期写入共享数据库的 `task_lifecycle_workflows`。
- `vw-agent` 把已保存 Workflow 写入同库的 `dify_workflows`，并按 UUID 提供 YAML。
- 旧 `task-workflows.json` 只在 gateway store 为空时迁移一次，迁移后不会删除用户旧文件。
- 桌面端遇到未加载或未知 lifecycle workflow 时应给出明确错误或降级提示，不静默创建本地定义。

阶段能力更适合作为项目级配置：

- 同一个 `marketing_campaign` 生命周期，不同项目可能把复盘配置为不同 `saved_workflow`。
- 同一个 `recruiting_pipeline` 生命周期，不同团队可能把初筛、面试或 Offer 配成不同能力。
- 内置 `code_review` / `git_merge` 是可选能力，不适合让业务 workflow 隐式继承。
- Workflow UUID 是本地保存的执行流程，不适合写死进全局生命周期模板。

推荐界面结构：

```text
工作流管理
  生命周期定义
    状态、语义角色、结果去向
  当前项目阶段执行配置
    每个阶段选择阶段能力
    saved_workflow 能力再选择已保存 Workflow
```

任务看板人员编排视图的阶段分配入口也可以显示同一组阶段能力控件，方便在分配负责人时同步选择
动作；实际保存仍进入项目的 `staff.project_state.stage_actions`。

## 架构回归清单

以下路径变更时必须保持 lifecycle-first，不回归到目标状态推断或手工移动补偿：

- Stage action：校验 capability 支持当前 status role，执行结果只提交 outcome，由 lifecycle bridge 解析下一阶段。
- Dispatch：只调度 lifecycle role 可调度且投影运行态为 `Queued` 的任务，`status_key` 和运行态不一致时拒绝调度。
- Policy：重试、超时、审核和合并收尾只通过 lifecycle outcome 推进，并同步 `status_key` / `status_role` 投影。
- Worker event：ack/start/submit/complete/fail 只接受 worker 生命周期事件，完成或失败后的阶段变化由 gateway 规则写入。
- Manual move：`command=move` 和批量移动只作为临时人工修正入口，不参与自动调度链路，不作为缺失 transition 的兜底。

## 简化心智模型

一句话：

```text
生命周期工作流决定“阶段和流向”。
语义角色决定“Agent Scheduler 如何看这个阶段”。
阶段能力决定“这个阶段具体执行什么动作”。
已保存 Workflow 是 saved_workflow 能力引用的业务自动化。
```

再短一点：

```text
状态负责位置。
角色负责执行调度类别。
能力负责具体执行。
Workflow 负责业务自定义。
```
