# 原生会话命令绑定

通用视频入口使用 `/shiju 剪辑 "视频绝对路径"`，无需创建下述项目绑定。正式模板位于 Workflow 应用的“通用云端视频剪辑”，通过模板设置 / YAML 查看和编辑；默认五路是单次运行的共享预算，最终工程写入串行。权限、恢复规则与本次证据见[通用云端剪辑验收](通用云端剪辑与分段并发验收.md)。以下配置和 sp7 实机记录属于既有项目绑定路径。

原生会话处理器可将项目命令确定性分派给现有 YAML 图执行器。工作流不是由模型自行决定是否调用；命中绑定后，当前消息直接执行图，图的最终答案和工具事件通过原会话流回传并持久化。

在项目根目录建立 `.shiju/workflow_commands.json`，并将样例 `crates/vw-agent/testdata/workflow/talking_head_cloud.yaml` 复制到项目内的 `.shiju/workflows/talking_head_cloud.yaml`：

```json
{
  "platform_id": "当前本地平台 ID",
  "company_id": "当前本地公司 ID",
  "commands": [{
    "command": "/shiju 剪辑",
    "workflow_file": ".shiju/workflows/talking_head_cloud.yaml",
    "inputs": {
      "source_file": "项目内原片的绝对路径",
      "shiju_skill_root": "当前原生客户端 shiju 技能包的绝对路径",
      "cloud_project_id": "用户已确认空间内的云端工程 ID",
      "style": "简洁清晰",
      "requirements": "真实原声、字幕与适量包装，先交预览"
    }
  }]
}
```

模型引用必须以当前客户端 `GET /v1/provider` 的 connected Provider 和模型目录为准。复制云端样例后，同时配置 prepare、plan、keywords、visuals、execute_cloud 五个节点的 `data.model.name`；例如用户当前指定的 `deepseek/deepseek-flash`。这只改变项目工作流，不需要修改全部会话的默认模型。

在该项目的原生会话中输入 `/shiju 剪辑 sp7`。直接输入 slash 和客户端技能菜单选择两种现有交互都能命中；后者使用客户端已有 `session_control_selection` 协议。命令必须在词边界匹配，有多个匹配时优先最长命令。未命中时保持普通会话行为。配置中的本地租户必须与当前会话一致；云端身份由客户端已有登录确定，不能把本地租户冒充为云端租户。

绑定只允许读取项目内的 YAML，拒绝越界符号链接、超限文件及运行时保留输入。运行器注入真实 `project_directory`，不接受绑定覆盖权限。原生 agent 节点沿用当前会话模型解析、工具执行器、工具能力范围、审批与取消；不能扩大父会话工具范围，也不调用外部 ACP。不要向 YAML 写入凭据。

云端样例顺序为：素材准备 → 校验真实转写 → 方案简报 → 并行关键词/画面建议 → 严格方案校验 → 云端执行 → 预览结果校验 → 最终答案。素材准备及执行节点通过当前客户端获取的已安装业务技能调用云端，不在本机处理媒体。校验失败时不进入云端执行，缺失就绪预览时不返回成功。实际预览仍须通过云端状态及查看页独立验收，不能把模型返回布尔值当作播放证据。样例仅交付预览，不最终导出。

原生 SSE 使用现有 `chat.tool` 事件，工作流节点名称为 `workflow`，payload 包含运行 ID、节点 ID、标题和耗时；不回传节点原始输入。子节点实际工具事件继续走原生工具卡片。停止当前聊天流会传播到图和正在执行的原生 agent；失败通过 `chat.error` 返回。当前工作流总 usage 未聚合，不以零值宣称没有模型消耗。

## 自动验证

按仓库约定领取共享 Cargo 槽位，同时设置绝对 `CARGO_TARGET_DIR` 和相同的 `CARGO_BUILD_BUILD_DIR`：

```bash
cargo test -p vw-agent --lib native_workflow -- --nocapture
cargo test -p vw-agent --lib build_chat_messages_ -- --nocapture
cargo test -p vw-agent --lib run_batch_tool_and_record_ -- --nocapture
cargo clippy --all-targets --all-features -- -D warnings
cargo build -p vw-cli --bin shiju
```

`native_workflow` 的 8 项回归覆盖真实 YAML 图执行、菜单命中、租户隔离、文件边界、失败、取消与工具限制，以及方案/预览门槛。外部模型与云端 agent 边界使用 fixture，不能替代真实视频验收。

实机首轮已证明原生聊天流命中图并启动素材准备，但暴露原生批处理执行器读取 `parameters` 与工具 schema 声明 `args` 不一致，以及路由模型的 `reasoning_content` 被消息层剥离。修复以现有工具 schema 和模型 `interleaved.field` 声明为准，保持旧 `parameters` 兼容和未声明模型的过滤行为。

实际 HTTP 抓包回归 `routed_reasoning_tool_history_survives_http_transport` 已通过：工具调用的推理字段、调用 ID、对应工具结果均到达传输层，内部来源标记不会外发。SDK 原有通用消息序列不能保存该字段，兼容 Chat 传输在模型明确声明此能力时使用已规范化的协议消息；Responses 和 Anthropic 保持原传输。

扩大到整个 `session::llm::aisdk::` 回归时，未修改的 `util_tests::openai_messages_to_aisdk_messages_converts_roles_and_tool_chain` 断言失败（期望 6 条、实际 5 条），触发现有平台 panic abort；本次没有修改该无关转换分支。相关 driver、stream、convert 模块另行聚焦验证。

真实视频第三轮执行已完成云端素材接入、ASR、转写校验、简报和并行分支；严格校验以 `invalid anchor` 停止云端写入。诊断发现一处锚点拼接时丢失原文标点。云端样例因此明确要求 anchor 原样选择一个时间戳 word，不能拼接或删标点；校验器未放宽。准备结果保存在项目 `.shiju-video/prepared.json`，续跑先核对云端对应素材和转写，避免重复上传或 ASR。

真实剪辑运行约 710 秒：素材/转写核验、简报、并行分支、严格方案校验、云端执行、预览校验与答案节点全部完成。云端独立回读确认竖屏 1080×1920、30 fps、1351 帧、44 个时间线元素；查看页显示 8 段文案、约 45 秒，包含真实视频、字幕和画面包装。实际编辑调用来自原生图的 `execute_cloud` agent 节点；Codex 负责实现、触发及只读验收。
