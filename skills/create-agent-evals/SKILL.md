# 创建 Agent 评测

把用户给出的场景转成可重复、可解释、能发现真实退化的评测资产。只创建或修改评测文件；不要优化被测实现。

## 开始前

1. 阅读 `AGENTS.md`、`evals/promptfoo/README.md`、`promptfooconfig.yaml`、`assertions.mjs` 和最接近的现有 YAML 用例。
2. 明确场景的目标行为、可观察结果、禁止行为、预算和所需环境。只有会改变判定语义的缺失信息才询问用户。
3. 检查现有 evaluation profile 和断言能否表达目标；优先复用，不复制评分逻辑。

## 场景契约

每个用例至少定义：

- 一个主要能力和一个清晰难度，不在一个用例中混合无关能力。
- 可从最终回答、工具轨迹、生成产物或外部可观察行为判定的成功条件。
- 不允许的写入、权限扩大、导航 fallback、失败工具或其它越界行为。
- 合理的工具调用上限；按完成任务所需预算设置，不用极低预算诱导跳过验证。
- 稳定的 `metadata.suite`、`metadata.batch`、description 和必要的筛选字段。

## 选择判定方式

按证据强度从高到低选择：

1. 独立黑盒检查：由评测器验证产物或运行行为，不依赖 Agent 自己编写的测试。
2. 工具轨迹检查：验证工具名称、操作、状态、参数、写入范围和调用预算。
3. 结构化结果检查：验证稳定标识、符号或结果字段。
4. 最终回答关键词：只用于事实型只读任务，不用于证明代码功能正确。

不要把“Agent 写了测试且测试通过”当作功能正确的唯一证据。coding 场景若要求行为正确，应规定稳定入口或 API，并增加独立 oracle；若当前断言框架无法执行该 oracle，应先最小扩展通用 profile，再添加用例。

## 生成规则

- 用例放在 `evals/promptfoo/tests/<descriptive-name>.yaml`，或在用户指定的现有文件中追加。
- 只读 RustCodeGraph 场景使用 `expectedOperations` 表达期望操作，使用稳定的 `expectedTerms` 表达必须回答的事实。
- coding 场景显式使用 `evaluationProfile: coding`，配置写入根、必需产物、排除产物、测试要求和预算。
- 如果现有字段不能表达成功条件，在 `assertions.mjs` 中添加可复用、命名明确的检查，并将其接入恰当 profile。不要为一个固定答案添加伪通用抽象。
- 断言检查结果，不检查措辞、标题或无意义的实现细节。
- 正例和失败原因必须可解释；配置错误应直接失败，不能静默记满分。
- 不从当前 Agent 输出反推期望结果。期望值必须来自源码、规格、fixture 或用户确认的行为。

## 验证

1. 运行 `evals/promptfoo/score.sh test`。
2. 静态复核 profile 路由、YAML 加载、正则转义、metric 权重和 hard gate。
3. 如果用户要求实际运行且 Gateway 可用，用最窄筛选运行新用例；否则报告尚未执行动态评测。
4. 实际运行失败时，区分评测基础设施失败、Agent 能力失败和断言设计错误。不得为了让当前模型通过而放宽正确性条件。

## 交付

简要列出新增场景、判定 oracle、运行命令和当前验证证据。明确哪些结果是确定性检查，哪些只是轨迹或文本信号。
