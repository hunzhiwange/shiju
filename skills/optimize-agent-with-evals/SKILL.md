# 基于评测优化 Agent

以既有评测作为冻结契约，改进被测 Agent 的正确性和效率。可以修改代码并重启用户纳入范围的本地 Gateway，但不得修改测试、断言、fixture、权重或通过阈值来制造提分。

## 输入与边界

接受测试 description、suite、batch、结果文件或它们的组合。开始前：

1. 阅读 `AGENTS.md`、`evals/promptfoo/README.md`、目标 YAML、`assertions.mjs` 和相关结果。
2. 记录目标筛选参数、Provider label、模型、重复次数、Gateway endpoint、git 状态和评测文件摘要；before 与 after 必须保持一致。
3. 如果用户只要求诊断，停在瓶颈报告，不修改代码或重启服务。
4. 保留用户已有改动；不要清理或覆盖无关工作树内容。

## 基线

- 先运行 `evals/promptfoo/score.sh test`。
- 使用最窄且稳定的筛选执行 `score.sh before`；一个用例可用 `--pattern`，一组用例优先使用 `--suite`、`--batch` 或 `--metadata`。
- 默认沿用 before/after 的 3 次重复。单次结果只能用于快速排错，不能作为稳定提升证据。
- 基线无法完成时先诊断环境、Provider、Gateway 或模型错误，不进入代码优化。

## 诊断

逐条查看失败原因、named metrics、最终回答、工具调用顺序与状态、参数、token、耗时和停止原因。将瓶颈归入一个主要类别：

- 正确性：缺事实、错误答案、产物行为不正确。
- 工具选择：未调用目标工具、错误 operation、fallback 或重复导航。
- 工具契约：描述不清、输入 schema 易误用、错误不可行动。
- 编排：上下文重复、无效循环、验证顺序不合理、过早或过晚停止。
- 实现：工具慢、失败、返回噪声过多或缺少关键字段。
- 环境/随机性：服务陈旧、索引状态、依赖、速率限制或模型波动。

先提出能被下一次评测证伪的单一假设。优先修复产生问题的最低层，不在上层提示词中绕过底层缺陷。

## 优化循环

每轮只处理一个主要瓶颈：

1. 选出能改善目标 metric 的最小生产代码变更。
2. 为行为变化添加或更新聚焦测试；不要触碰冻结的 Promptfoo 用例和断言。
3. 运行聚焦验证，并按仓库规则运行 `cargo clippy --all-targets --all-features -- -D warnings`。
4. 只有代码实际影响运行中的 Gateway 时才重启。终止已明确识别、由当前评测使用的进程或会话；禁止使用宽泛 `pkill`、按名称批量杀进程或影响无关服务。
5. 使用仓库文档命令启动 Gateway，例如 `cargo run -p vw-cli --bin shiju -- gateway --host 127.0.0.1 --port 42617`，并在 `http://127.0.0.1:42617/v1/health` 成功后复测。
6. 使用完全相同筛选执行 `score.sh after` 和 `score.sh compare`，检查总体、逐任务和逐 metric delta。

默认最多进行 3 轮代码优化。用户指定其它上限时遵从。达到上限、连续两轮没有改善、发生回归、结果明显不稳定或需要扩大权限/范围时停止并报告，不继续试探性修改。

## 判断是否真的改善

只有同时满足以下条件才保留优化：

- hard gate、正确性和通过率不下降。
- 目标 metric 改善，或原失败稳定转为通过。
- 若目标是压缩工具步骤，完成质量保持不变，并且实际工具调用数、token 或耗时至少一项下降；不能靠跳过必要验证降低调用数。
- 没有削弱安全策略、错误检查、工具能力或评测判定。

如果差异只出现在单次运行或低于自然波动，将结果标为“不确定”，不要宣称提升。无法改善时给出瓶颈位置、证据、已排除假设和下一项最有价值的实验。

## 回退与交付

每轮审查差异，只回退本轮由当前任务引入且被证据否定的改动；不要使用破坏性 git 命令，也不要覆盖用户改动。

最终报告目标测试、before/after、关键 metric、工具调用变化、修改位置、验证命令、剩余瓶颈和是否达到停止条件。评测失败但诊断完成时，明确区分“能力未改善”和“环境阻塞”。
