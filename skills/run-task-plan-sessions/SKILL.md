# 执行任务计划会话

将用户指定的 `prompt.md` 作为完整计划的调度入口。主会话只读取计划状态并使用 `SessionTool` 创建、跟踪、等待、读取和续发可见任务会话；不代替任务会话实现代码、运行验证或修改编号任务文件。

## 读取计划

1. 读取用户指定的 `prompt.md`。未指定路径时，仅在当前工作区存在唯一合理的 `.plans/*/prompt.md` 候选时自动选择；存在多个候选时请用户指定。
2. 按 `# 批次 N` 和 `## 任务 N` 解析顺序，将每个任务下的 `text` 代码块原样作为该会话的完整初始提示，不合并、删减、改写或补充。
3. 从提示中解析对应编号任务文件，读取其中的批次、依赖批次和 `状态：`。`plan.md` 仅作只读架构参考；主会话不修改任何计划文件。
4. 每个编号任务只对应一个任务会话。记录每次 `create` 返回的 `session_id`，后续等待、读取、恢复和回归始终复用该会话。

## SessionTool 接口

所有调用都使用原生 `SessionTool`，且只访问当前主会话创建的、同一工作区内的可见任务会话。

- 创建：`{"action":"create","title":"<任务标题>","prompt":"<完整任务提示>"}`。创建会异步启动，返回 `session_id` 和 `running`；模型继承当前会话的非自动选择，不传项目、环境、模型或推理参数。
- 列举：`{"action":"list"}`。用于恢复调度上下文或核对本主会话创建的任务，不替代本地记录的任务与 `session_id` 映射。
- 状态：`{"action":"status","session_ids":["<session_id>"]}`。状态只有 `queued`、`running`、`succeeded`、`failed`。
- 读取：`{"action":"read","session_id":"<session_id>","max_chars":65536}`。`max_chars` 必须为正整数且最多 65536；结果可能为截断的最近消息，只用于理解本轮结果或生成恢复提示。
- 续发：`{"action":"send","session_id":"<session_id>","prompt":"<恢复或回归提示>"}`。仅在目标为 `succeeded` 或 `failed` 后调用；对 `queued` 或 `running` 目标会明确失败。
- 等待：`{"action":"wait","session_ids":["<session_id>"],"condition":"any","timeout_ms":60000}`。`condition` 为 `any` 或 `all`，单次最长 60000ms；`timed_out: true` 只表示本次有界等待结束。

## 批次调度

1. 严格按批次号从小到大调度。任务的所有依赖批次达到实现阶段的可接受状态前，不启动该任务。
2. 同一批次最多同时运行 5 个任务会话。超过 5 个任务时分波创建；当前波释放并发名额后再创建同批次下一波。
3. 对每个可运行任务调用一次 `create`：`title` 使用 `prompt.md` 的任务标题，`prompt` 使用任务完整代码块，并立即保存返回的 `session_id`。
4. 对活动会话使用 `wait` 有界等待。多目标通常使用 `condition: "any"` 以便及时处理首个终态；需要收齐当前波时可使用 `all`。每次 `timeout_ms` 不超过 60000。
5. 等待超时时，用返回快照或 `status` 确认状态；目标仍为 `queued`/`running` 时继续有界等待，不调用 `send`，不将超时误判为阻塞或失败。
6. 目标进入 `succeeded` 或 `failed` 后，按下方状态机读取编号任务文件；仅在需要理解失败或组织续发内容时调用 `read`。会话终态只代表本轮结束，不代表任务完成。

## 任务状态机

编号任务文件是完成判定的唯一来源。会话消息和 `succeeded`/`failed` 只能辅助恢复，不能覆盖文件状态。

- **已完成并删除**：编号任务文件不存在。任务最终完成，可满足后续依赖，也不进入回归队列。
- **已完成，待回归**：文件保留且状态精确为 `已完成，待回归`。实现阶段完成，可满足后续依赖；保存原 `session_id` 并加入最终回归队列。
- **已阻塞**：文件保留且状态精确为 `已阻塞`。进入阻塞恢复流程，不立即终止整个计划。
- **未完成**：文件仍为 `未开始`、保留 `已完成` 而未按契约删除、使用未定义状态，或本轮结束后无可判定结果。等待目标终态后向原会话 `send`，要求完成剩余工作并按任务契约更新或删除文件；不得新建替代会话。

即使 SessionTool 返回 `failed`，也先检查任务文件：任务会话可能已经留下可恢复证据或完成实现。即使返回 `succeeded`，也不能仅凭最终文本宣布完成。

## 阻塞恢复

1. 先等待同批次其他活动任务结束。若阻塞来自共享文件、构建产物或同批次工作，基于最新共享工作区在原会话中恢复。
2. 确认目标已为 `succeeded` 或 `failed`，必要时用 `read` 获取最近消息，再用 `send` 要求它重读任务文件中的证据并继续。主会话不自行修复或改写任务状态。
3. 恢复时区分：
   - 瞬时命令、构建或环境失败：重试或采用仓库已有的等价验证。
   - 无关本任务的回归失败：实现与聚焦验证已完成时，按任务契约标记 `已完成，待回归`，不得伪造通过证据。
   - 可合并的共享工作区冲突：等待相关会话结束后，基于最新文件继续。
   - 真正缺少用户决策、权限或外部状态：保留 `已阻塞` 和具体证据。
4. 相同阻塞重复时不要求重复无意义检查。继续调度所有不依赖该阻塞项的任务；依赖它的后续任务保持未启动。
5. 只有没有活动会话、没有其他可运行任务，且原会话已证明需要新的用户决策、权限或外部状态时，才停止并向用户报告真实阻塞。

恢复提示可保持简短：

```text
请继续执行原任务。重读任务文件中的阻塞或未完成证据，基于当前共享工作区重试，并穷尽任务范围内的安全替代方案。实现与聚焦验证已完成、仅剩无关回归失败时，按任务契约标记为“已完成，待回归”；只有真正需要用户决策、权限或外部状态时才保留“已阻塞”。
```

## 最终回归

1. 只有所有非真实阻塞任务都已删除或进入 `已完成，待回归`，才启动最终回归；仍未满足依赖的任务不能提前启动。
2. 对回归队列中的任务复用已记录的原 `session_id`。确认会话处于 `succeeded` 或 `failed` 后，用 `send` 要求执行延后的回归验证；不创建新回归会话，不由主会话运行测试。
3. 回归最多同时续发 5 个原会话，并使用最长 60000ms 的有界 `wait` 持续跟踪。超时后仍为活动状态则继续等待。
4. 每轮结束后重新应用任务状态机。回归通过后应由原会话删除编号任务文件；与本任务相关的失败由原会话诊断、修复并重试，真正需要用户决策、权限或外部状态时才保留阻塞。

回归提示可保持简短：

```text
所有可运行计划任务的实现阶段已结束。现在执行任务文件中延后的回归验证，基于最新共享工作区诊断并修复与本任务相关的失败。获得所需证据后删除任务文件；只有真正需要用户决策、权限或外部状态时才标记为“已阻塞”。
```

## 停止条件与边界

- 所有编号任务文件都已删除时，计划执行完成。
- 只有存在不可突破的真实阻塞、没有活动会话且没有其他可运行任务时，计划才以阻塞状态停止。
- 主会话只调度会话和读取计划状态，不代做任务、不修改代码或任务文件、不创建自动化、分支、提交或 PR。
- 不使用 Codex App 的项目查找、worktree、模型选择、推理强度或 UI 指令；创建的原生任务会话自然显示在当前工作区。
- 最终回复只报告整体结果：`计划执行完成。` 或 `计划未完成：N 个任务仍阻塞。`，不逐项复述任务实现。
